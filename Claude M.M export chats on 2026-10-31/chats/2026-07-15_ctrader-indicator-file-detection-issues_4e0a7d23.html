MILLARD2026-07-15 17:59 UTC

I'm using VS Code to develop indicators for cTrader. Both the CODEX and Claude extensions will edit, compile, and build them, creating an .algo file.

I'm having an intermittent, inconsistent problem with these indicators.

Usually, simply by copying the .algo file to the platform's \Indicator folder will cause it to show up as "new" in cTrader's indicators list, even though the platform is running, even though the indicator was running on a chart.

Sometimes, though, there's no trace of it anywhere, and I have to close and reopen the platform, with is a real pain in the ass given how many changes I make to the code.

I've tried double-clicking on the .algo file, it prompts me asking if I want to replace the existing one, I click yes, and still -- nothing happens. No indy to be found.

Has anyone found a fix or workaround for this problem?

CLAUDE2026-07-15 18:00 UTC

No real fix exists — it's a known cTrader bug, not something you're doing wrong. Multiple developers report the same thing on 5.x: rebuilds reload the first time or two, then silently stop registering until a full platform restart, even when the .algo compiled clean, and Spotware shipped a hotfix (5.0.38) for indicators randomly unloading, but reports continued after it. Spotware has never given a reliable workaround.

What actually works around it in practice:

  1. Rename each build. Give the .algo a bumped name (e.g. TTEM_v37.algo). cTrader treats it as a brand-new indicator and picks it up immediately, every time — that's why your copies "usually" show up as new. The failure mode only hits replacements of an already-loaded file, because the old assembly stays locked in cTrader's process. Downside: the indicator list clutters up and you re-add to the chart each time, but it's the only method that never needs a restart.

  2. Detach before replacing. Remove the indicator from all charts (and close any Algo-tab view of it) before copying the new .algo over. Replacing while an instance holds the old DLL loaded is exactly when the stale-assembly failure happens.

  3. If you're already stuck (no trace anywhere), restart is the only recovery — double-clicking and "replace" won't unstick it, as you've found.

Given how many builds you do a day, option 1 with a build-number suffix automated into your VS Code build step is the workflow most cTrader devs settle on.

CLAUDE2026-07-15 18:03 UTC

That spinner is the same bug made visible — the installer is waiting to swap in the new file, but the running platform still has the old assembly loaded and locked, so the install never completes. It'll spin forever; clicking X doesn't cancel anything useful.

Once you see that hang, the platform is already in the stuck state: restart is the only way out. The value of the toast is as an early warning — if you double-click and it installs instantly, you're fine; if it spins, don't waste time hunting the indicators list, just restart. Detaching the indicator from every chart before installing is what prevents the hang in the first place.
