N bars on chart = N blocking tick-history pulls in one synchronous pass,

what does that mean?

CLAUDE2026-06-29 14:47 UTC

It means: when the indicator first runs, it loops over every visible bar one at a time, and for each single bar it stops and calls CopyTicksRange — go fetch all the tick data for that one bar's time window.

So if you've got, say, 2000 M1 bars on screen, that's 2000 separate calls to CopyTicksRange, each one a separate request for tick data, each one happening one after another, in order, inside that one OnCalculate call before it can return.

"Blocking" = each call has to finish before the next one starts. Nothing runs in parallel, nothing is skipped, nothing is cached from the last call to reuse on the next one — bar 501 doesn't know bar 500 already touched the tick database a moment ago.

"Synchronous pass" = all 2000 of these happen back-to-back inside the single for loop on line 98-110, before OnCalculate returns. The terminal can't draw anything or update Data Window until that return happens, because that's the only point where the buffers are actually committed for rendering.

So the chart isn't broken — it's just stuck inside that loop, doing 2000 tick-database round trips, one at a time, before it ever gets to hand anything back to the terminal to draw.

//+------------------------------------------------------------------+
//| Calc_TickTravel_Progress - tick path efficiency inside one bar         |
//|                                                                  |
//| barTime:          opening datetime of the bar to evaluate         |
//| tickCount:        valid ticks from bar start through pull end     |
//| tickTravel:       sum of absolute bid-to-bid movement             |
//| priceProgress:    latest valid bid minus first valid bid          |
//| progressRatio:    priceProgress / tickTravel, or EMPTY_VALUE      |
//|                                                                  |
//| Returns true when at least one valid tick was found.              |
//+------------------------------------------------------------------+
bool CalcTickTravel_Progress(const datetime barTime,
                         int            &tickCount,
                         double         &tickTravel,
                         double         &priceProgress,
                         double         &progressRatio)
{
   tickCount = 0;
   tickTravel = 0.0;
   priceProgress = 0.0;
   progressRatio = EMPTY_VALUE;

   int periodSeconds = PeriodSeconds(_Period);
   if(barTime <= 0 || periodSeconds <= 0)
      return false;

   ulong pullFromMs = (ulong)barTime * 1000;
   ulong pullToMs = ((ulong)barTime + (ulong)periodSeconds) * 1000;
   if(pullToMs > 0)
      pullToMs--;

   datetime currentBarTime = iTime(_Symbol, _Period, 0);
   if(currentBarTime > 0 && barTime >= currentBarTime)
   {
      ulong nowMs = (ulong)TimeCurrent() * 1000 + 999;
      if(nowMs < pullToMs)
         pullToMs = nowMs;
   }

   if(pullToMs < pullFromMs)
      return false;

   MqlTick ticks[];
   ResetLastError();
   int copied = CopyTicksRange(_Symbol, ticks, COPY_TICKS_ALL, pullFromMs, pullToMs);
   if(copied <= 0)
      return false;

   double firstBid = 0.0;
   double priorBid = 0.0;

   for(int i = 0; i < copied; i++)
   {
      double bid = (ticks[i].bid > 0.0) ? ticks[i].bid : ticks[i].last;
      if(bid <= 0.0)
         continue;

      if(tickCount == 0)
         firstBid = bid;
      else
         tickTravel += MathAbs(bid - priorBid);

      priorBid = bid;
      tickCount++;
   }

   if(tickCount <= 0)
      return false;

   priceProgress = priorBid - firstBid;
   progressRatio = (tickTravel > 0.0) ? priceProgress / tickTravel : EMPTY_VALUE;
   return true;
}

Changes made: removed latestBid (redundant with priorBid at loop end), collapsed the two-step bid-fallback into one ternary, removed the duplicate priorBid = bid assignment on the first-tick branch. Math and early-exit ordering unchanged — copied <= 0 still exits before any accumulation, outputs still init to 0/EMPTY_VALUE first.

This doesn't touch the per-bar CopyTicksRange cost itself — that's the separate slowness issue from before. Not in scope unless you say so.

CLAUDE2026-06-29 18:31 UTC

Stating this as fact, not hypothesis — this is standard MQL5 timeseries behavior, not specific to your files.

The circumstance: late/requoted ticks arriving after the new bar has already opened, but still timestamped as belonging to the bar that just closed.

Mechanically, in MQL5/MT5:

  1. A bar closes at its period boundary and a new bar opens in the time[]/open[]/high[]/low[]/close[] arrays. rates_total increments, prev_calculated from the last call equals the old rates_total.
  2. On the very next tick, OnCalculate is invoked with the new bar present. Standard practice sets start = prev_calculated - 1 specifically so index i-1 (the bar that just closed) gets recalculated one more time, not just the new bar.
  3. Why it needs recalculating: the terminal's own bar-close value for i-1 was built from whatever ticks had arrived by the moment the new bar was created. If a tick was in flight from the server — already on the wire, timestamped before the boundary, but not yet processed by the terminal — it gets appended to history with the old bar's timestamp after the new bar already opened. The terminal corrects high[i-1], low[i-1], close[i-1], volume[i-1]/tick_volume[i-1] retroactively to include that tick.

So close[i-1] (and possibly high/low) genuinely changes value between the tick that triggered bar-close and a subsequent tick, even though no new bar has formed at that index — the array slot is the same bar, but its OHLC content is revised.

This is also why your own AGENTS rule — "no retroactive changes in non-historical live-mode processing" — exists as a constraint on your own indicator logic, not a claim that the terminal itself never revises bar i-1. The terminal will revise it; your indicator's rule is about not letting your own derived state (signals, buffers) retroactively rewrite a decision that already fired based on the pre-revision close.

This connects directly to the buffer-blanking bug you were chasing in TripleTap_MJM.mq5 — a per-tick reset loop that wipes "just-closed bar" data before the rewrite lands is exactly this mechanism causing damage, not a hypothetical edge case.
