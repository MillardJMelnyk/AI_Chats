CLAUDE2026-05-08 17:50 UTC

Millard, solid bones on this one. The concept is clean and the live/historical split is structurally sound. But there are real bugs and a couple of architectural concerns worth addressing. I'll go through them in order of severity.

BUG 1 — Silent zero-fill where tick history doesn't exist (misleading data)

CopyTicksRange returns tick data only as far back as the broker stores it — typically 1–3 months. For every bar older than that, the function returns <=1 ticks, the function bails early, and the buffers get 0.0. Zero travel looks like maximum decisiveness — the opposite of "no data." This is the single worst bug because it silently corrupts the visual read.

Fix: initialize buffers to EMPTY_VALUE and set PlotIndexSetDouble accordingly. Then only write real values when CopyTicksRange actually returns usable data.

BUG 2 — Live bar undercounts travel (tick-skipping under load)

OnCalculate is not guaranteed to fire on every tick. When the terminal is busy or ticks arrive in bursts, intermediate ticks get batched — close[currentBar] jumps from tick N to tick N+3, and the movements N→N+1→N+2→N+3 collapse into a single N→N+3 delta. The live bar will systematically undercount travel relative to the historical recalculation that uses CopyTicksRange (which captures every recorded tick). The value then jumps when the bar closes and gets reconciled.

This is inherent to the OnCalculate-with-close[] approach. The only real fix is to use CopyTicksRange on the live bar too (from time[currentBar] to now), replacing the accumulator entirely. That's heavier per tick, but it's the only way to be honest.

BUG 3 — No EMPTY_VALUE initialization on buffers

Related to Bug 1 but distinct. You never call PlotIndexSetDouble(n, PLOT_EMPTY_VALUE, EMPTY_VALUE) for any plot, and you never ArrayInitialize the buffers to EMPTY_VALUE on a full recalc. So every unwritten index is 0.0, not empty. Even if you fix Bug 1, a future code path that skips a bar for any reason will leave a phantom zero.

BUG 4 — Full recalc performance is unbounded

When prev_calculated == 0, the loop calls CopyTicksRange once per bar for every bar on the chart. On XAUUSD M1 with, say, 50,000 bars visible, that's 50,000 separate tick-range queries. This will hang the terminal for a significant period on first load or any chart refresh that resets prev_calculated. There's no throttle, no progress, and no way for the user to know what's happening.

Practical fix: cap the historical lookback to match actual tick availability (query the broker's earliest tick timestamp once in OnInit, then skip bars before it) and/or limit to a configurable max-bars parameter.

BUG 5 — start on incremental update can re-query a bar that's already correct

When prev_calculated > 0 and a new bar forms, start = prev_calculated - 1 re-runs CalculateHistoricalTravel on the just-closed bar. This is intentional reconciliation and produces the correct value — so it's not wrong in output. But it IS a redundant CopyTicksRange call on every new bar, and more importantly, it silently overwrites the tick-accumulated value with the historically-calculated one. If those two values ever diverge significantly (Bug 2 scenario), there's no diagnostic visibility into that discrepancy. Worth logging.

DESIGN OBSERVATIONS (not bugs, but relevant to purpose):

D1 — Raw travel isn't normalized. A 5.0-travel bar during London session means something very different from 5.0 during Asian session. For a decisiveness-vs-indecision read, travel divided by bar range (high - low) gives you an efficiency ratio: ~1.0 = perfectly decisive, >>1.0 = highly indecisive. Raw travel just tracks volatility level. Up to you whether that matters for your use case.

D2 — Positive/Negative travel decomposition. You're splitting into directional components, which is useful. But note: in a perfectly decisive bullish bar, PositiveTravel ≈ Travel and NegativeTravel ≈ 0. In a perfectly indecisive bar, PositiveTravel ≈ NegativeTravel ≈ Travel/2. So the ratio of positive-to-negative tells you more about decisiveness than the absolute values do. The current display makes the user eyeball this rather than showing it directly.

D3 — GetTravelTickPrice bid-first fallback is fine for XAUUSD but worth a comment that this assumes a bid-quoted instrument. On exchange-traded symbols, last is the meaningful price and bid can lag.

Want me to produce a corrected file with the fixes applied? The main ones are: EMPTY_VALUE initialization, tick-availability boundary detection, and optionally the live-bar CopyTicksRange replacement for Bug 2.

CLAUDE2026-05-08 18:44 UTC

Efficiency = Travel / Range (high − low). Here 13.33 / ~2.11 = 6.3175. Price traveled 6.3x the bar's net range — lots of back-and-forth. A value of 1.0 would mean price moved in a straight line from one end of the bar to the other. Higher = more indecisive.

MILLARD2026-05-08 18:52 UTC

Efficiency is a weird way to put it. Isn't this a measure of indecision?

CLAUDE2026-05-08 18:52 UTC

Yes. Higher values = more indecision. Calling it "Efficiency" inverts the meaning — efficiency implies better as the number goes up, but here it's the opposite. Something like "Churn" or "Thrash" would read correctly: more churn = more indecision, less = decisive.

MILLARD2026-05-08 18:55 UTC

What about making it a churn rate? How would you factor time into it?

CLAUDE2026-05-08 18:55 UTC

Churn / elapsed time within the bar. On M1 every closed bar is 60 seconds, so for historical bars it's just a constant divisor — doesn't change the shape. But on the live bar it matters: a churn of 6.0 in the first 15 seconds is a very different animal than 6.0 after 55 seconds. The rate captures intensity of indecision, not just amount.

For the live bar: elapsed = current tick time minus bar open time. Churn Rate = (Travel / Range) / elapsed seconds. Could express it per-minute to keep the numbers readable on M1.

MILLARD2026-05-08 18:56 UTC

which better indicates indecision?

CLAUDE2026-05-08 18:57 UTC

Churn without time. A bar where price thrashed 6x the range was indecisive regardless of whether that took 10 seconds or 55 seconds. Time dilutes the signal — a burst of wild oscillation early in the bar followed by calm would show a low rate, even though the indecision clearly happened.

Rate answers a different question: how frantically indecisive was it. Interesting, but secondary.

MILLARD2026-05-08 19:14 UTC

I think raw travel should be divided by raw body spread, not hi/lo spread

CLAUDE2026-05-08 19:14 UTC

That's cleaner. Body = |close − open| = what the bar actually accomplished directionally. Travel / Body asks: how much total movement did it take to get there? A ratio of 1.0 is impossible (travel is always ≥ body), so the theoretical minimum is 1.0 = perfectly decisive, and it scales up from there with no ceiling.

High−low is contaminated — the wicks are themselves evidence of indecision, so you'd be dividing indecision by indecision.

Doji bars (body near zero) send the ratio toward infinity, which is exactly right — a doji is maximum indecision.
