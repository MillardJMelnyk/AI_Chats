Found it. Plain-English diagnosis:

The ZZ line is being plotted as DRAW_SECTION (line 78), which connects every non‑EMPTY_VALUE cell. But on every tick — i.e., every OnCalculate where prev_calculated != 0 — this block runs:

int zz_count = rates_total - signal_start;          // signal_start = prev_calculated - 1
ArrayResize(zz_values, zz_count);
CopyBuffer(g_zz_handle, 0, 0, zz_count, zz_values); // <-- only the LAST zz_count bars
for(int zz_i = 0; zz_i < zz_count; zz_i++)
   BufZigZag[signal_start + zz_i] = zz_values[zz_i];

On a normal incremental tick signal_start = prev_calculated - 1, so zz_count is 1 or 2. You're copying ZZ values for only the last one or two bars and writing them into the tail of BufZigZag. The rest of BufZigZag (every prior bar) is untouched — meaning it holds whatever it held last tick only if it survived. But it doesn't survive: BufZigZag is reinitialized to EMPTY_VALUE on the first-pass branch (line 4539), and any time the terminal triggers a full recalc (history sync, timeframe nudge, server adjustment, indicator reattach), prev_calculated resets to 0 and you re-init the whole buffer — but the incremental path never repopulates the historical bars. So between full recalcs you've got a DRAW_SECTION with only the most recent 1–2 cells filled (a stub at the right edge), and on every full recalc the tail briefly snaps to the full ZZ before the next incremental tick paints over only the newest bars again. That's the flicker — the section line is being drawn from an almost-entirely-EMPTY_VALUE buffer most ticks.

There's a second, related issue masking the bug: the guard zz_ready >= rates_total is comparing BarsCalculated (which is a bar count) against rates_total directly. For a fully ready subordinate this is fine, but it doesn't help you here because even when it passes, you're still only copying the tail.

Two fixes, pick one:

  1. Copy the full ZZ buffer on first pass, then only update the tail incrementally. On prev_calculated == 0, do CopyBuffer(g_zz_handle, 0, 0, rates_total, …) and write into BufZigZag[0..rates_total-1]. On subsequent ticks, copy just the last rates_total - prev_calculated + 1 bars as you're doing now. The historical cells then persist across ticks.
  2. Copy the full buffer every tick (simpler, slightly more expensive): replace zz_count = rates_total - signal_start with zz_count = rates_total and write into BufZigZag[0..rates_total-1].

OK, that confirms it. Reassessed answer:

The only place that empties BufZigZag is ClearIndicatorBuffers, called only on prev_calculated == 0. So between full recalcs the historical cells should persist. The flicker isn't coming from those cells being wiped.

The flicker is coming from the first-pass population itself never happening.

Look at the gating: the ZZ copy block is inside Loop 2 (for i = signal_start … rates_total) and only runs when i == signal_start. On prev_calculated == 0, start_bar = 0, but signal_start is then derived from g_chart_signal_start = ComputeSignalStartBar(...) — which for a chart with substantial history is going to land far to the right of bar 0 (it's the warmup-respecting starting bar for the signal pipeline). So on the very first pass, signal_start is something like rates_total - N where N is the recent window the signal loop processes, and zz_count = rates_total - signal_start only covers that recent window. Every bar to the left of signal_start keeps the EMPTY_VALUE from ClearIndicatorBuffers and is never written.

Then on every subsequent tick, signal_start recomputes to roughly prev_calculated (or prev_calculated - 1), zz_count is 1 or 2, and the copy writes only the rightmost 1–2 cells. The historical cells from the first pass — the ones in the [g_chart_signal_start, rates_total) window — do persist, but everything to the left of g_chart_signal_start remains EMPTY_VALUE forever.

That gives you a DRAW_SECTION line that exists only over the recent signal window. The "flickering / fully repainted every tick" appearance is the section line's left endpoint sliding/snapping as the subordinate ZZ's most recent leg revises (ZZ legs revise their last pivot until confirmed), combined with the section auto-bridging across EMPTY_VALUE gaps differently as new cells land — DRAW_SECTION connects non-empty cells, and when the last 1–2 cells get rewritten each tick from a still-revising subordinate, the rightmost segment redraws every tick. It looks like a full repaint because the visible portion of the line is essentially only the live-revising tail.

Two compounding contributors worth flagging:

  • The ZZ population is gated on i == signal_start inside Loop 2, but it has nothing to do with the per-bar signal logic. It should be a one-shot block before the loop, with separate first-pass-vs-incremental behavior — full copy on prev_calculated == 0, tail copy thereafter — and the copy range should be measured from a fixed left edge (e.g., g_chart_signal_start or 0), not from a per-tick signal_start that creeps rightward.
  • The subordinate Ind_ZigZag_MJM itself revises its open leg each tick (that's normal ZZ behavior), so even with a correct copy, the rightmost segment of the section line will redraw as the live pivot moves. That's expected ZZ behavior, not a bug — but it'll be much less visually disruptive once the historical cells are actually populated and the section line has a stable left side.
