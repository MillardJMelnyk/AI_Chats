I'm getting no output of any kind from this indicator. Where are the bugs?

CLAUDE2026-03-31 17:06 UTC

Three bugs:

Bug 1 — Full reinitialize on every tick (lines 79–81)

ArrayInitialize(ZZ, EMPTY_VALUE);
ArrayInitialize(HighMap, 0.0);
ArrayInitialize(LowMap, 0.0);

This wipes all buffers on every call to OnCalculate, including on live ticks. That alone would cause flickering/no output in some builds, but it's also just wasteful. Move these into OnInit, or guard them with if(prev_calculated==0).

Bug 2 — Reversal check fires too early, before the leg spread is confirmed (lines 111–129)

The candidate update and the anchor-commit happen inside the same loop iteration with no gap. The moment candidateNow is a new extreme, you immediately commit it as a pivot and flip direction. That means a leg is "confirmed" on the very bar that extended it, with no subsequent bar to validate. On the next tick, ArrayInitialize (Bug 1) wipes it. Combined with Bug 1 this produces zero visible output.

The fix: only commit and flip when a reversal is detected — i.e., the opposite direction move from candidateBar exceeds InpMinSpread and satisfies InpMinBars. Until then, just keep extending the candidate.

Bug 3 — dir==0 branch can permanently stall (lines 95–109)

After the first anchor, dir is set. But anchorPrice is initialized to close[0]. If bar 0's close is exactly between a symmetric up/down move, the tie-breaker on line 108 works. But if neither upMove nor downMove reaches InpMinSpread before periodsFromAnchor >= InpMinBars, the loop keeps continue-ing with dir still 0 and anchorBar stuck at 0 forever. Once dir is finally set, Bug 2 immediately commits a pivot and flips — but the next iteration restarts with a new anchorBar at a potentially far-back bar with stale price context.

Minor but real: initialize anchorPrice to low[0] (or high[0]) depending on your intended first leg direction, or use (high[0]+low[0])/2.0 to be neutral.

Summary of fixes needed:

# Location Fix
1 Lines 79–81 Move ArrayInitialize calls into OnInit or guard with prev_calculated==0
2 Lines 111–129 Don't commit pivot on the same bar that extends it; require a confirmed reversal from a subsequent bar
3 Line 84 Use midpoint or appropriate extreme for anchorPrice at bar 0

Bug 2 is the primary cause of no output. Bug 1 would destroy any output that survived Bug 2.

CLAUDE2026-03-31 17:08 UTC

Understood. The design intent is to keep the pivot at the running extreme and move it forward as the leg extends — that's correct ZigZag behavior.

So Bug 2 withdrawn.

That leaves Bug 1 as the primary cause of no output — wiping all buffers on every tick destroys whatever was plotted on the previous call. With the full recalc loop running from bar 0 each time, the pivots are rewritten correctly, but then on a live tick they get wiped before anything renders.

Bug 3 is still real but would only cause a stall on the very first leg under specific price conditions, not a total blackout.

The one fix that restores output: guard the ArrayInitialize calls:

if(prev_calculated == 0)
  {
   ArrayInitialize(ZZ, EMPTY_VALUE);
   ArrayInitialize(HighMap, 0.0);
   ArrayInitialize(LowMap, 0.0);
  }

However — since you're doing a full recalc from bar 0 every call anyway (no incremental logic), you actually need those initializes on full recalc but not on tick updates. The cleaner fix is to also add incremental logic so you're not re-scanning all bars on every tick, but that's a separate matter. The guard above will at minimum make the indicator produce visible output.

CLAUDE2026-03-31 18:44 UTC

The last pivot bar is being stored in ZZ[], and DRAW_SECTION draws a line from the previous pivot to it — but then it also draws a line from that pivot down to bar 0 (price 0.0), because DRAW_SECTION connects every non-EMPTY_VALUE point.

The dangling vertical line is the ZZ connecting the last confirmed pivot to an uninitialized or zero-valued buffer cell near the right edge.

The bug: On the reversal commit (lines 335–339), pivotBar is set to i and stored. But the previous pivotBar was ClearPivot'd (line 318) only when the same-direction extreme moved. When a reversal triggers, the old pivotBar is never cleared before the new one is written. So you can briefly have two non-EMPTY_VALUE cells — the old pivot and the new reversal bar — with a spurious segment between them.

That's not the vertical though. The vertical drop to the bottom is DRAW_SECTION drawing from the last pivot to a buffer cell that contains 0.0 instead of EMPTY_VALUE.

Root cause: ArrayInitialize(ZZ, EMPTY_VALUE) only runs on full reset. On incremental ticks, ClearRecordedPivots clears touched bars to EMPTY_VALUE — but pivotBar on the final iteration (the still-forming leg tip) gets written to ZZ[] and tracked, then on the next tick it gets cleared and rewritten. If any bar in that sequence was missed by TrackTouchedBar, it stays as 0.0, not EMPTY_VALUE, and DRAW_SECTION draws to it.

Fix: In ClearPivot, initialize to EMPTY_VALUE, which you already do. Verify that every StorePivot call is paired with a TrackTouchedBar call — specifically check the reversal block at lines 335–340. pivotBar there is set to i and stored, but the previous pivotBar is never cleared or re-tracked before being abandoned. Add:

ClearPivot(ZZ, HighMap, LowMap, pivotBar);  // clear old pivot tip before reassigning
TrackTouchedBar(pivotBar);                   // track the clear
pivotBar = i;
pivotPrice = oppositePrice;
pivotDir = searchDir;
StorePivot(ZZ, HighMap, LowMap, pivotBar, pivotPrice, pivotDir);
TrackTouchedBar(pivotBar);
