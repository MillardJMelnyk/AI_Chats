Here are the meaningful differences between the MQL5 indicator and the Python script:

1. Cocking logic runs in the wrong place (ordering bug)

In the MQL5, the cocking loop (lines 1822–1861) runs before the cross/trigger/signal logic — it's inside the if(!g_spikeActive) block that precedes rawCrossUp/rawCrossDn computation. In the Python, the cocking loop (lines 724–745) runs after the signal-commit block and after the cross-after-signal reset. This means in Python a bar that fires a signal can also update the cocked state on the same iteration, and the cocked state available to the trigger check on bar i reflects cocking from bar i's own pass rather than from the previous iteration's pass. This is the most consequential difference — it will shift signal timing.

2. !g_spikeActive guard missing from cocking in Python

The MQL5 wraps the entire cocking block in if(!g_spikeActive). The Python cocking block (lines 724–745) has no spike-active guard at all, so it can update cocking state during an active spike window.

3. !g_spikeActive guard missing from several Python blocks

The MQL5 guards the cross-after-signal reset (line 2412), the blackout-pending retrace check (line 2140), and the aggressive flip-check (line 2158) with && !g_spikeActive. In Python, the cross-after-signal reset (line 705) does check not state.spike_active, but the blackout-pending retrace (line 625) and the aggressive flip-check (line 637) do not — they'll fire during an active spike when the MQL5 would suppress them.

4. Non-aggressive backstop also fires in aggressive mode

In the MQL5 (line 2085), the backstop guard is !isAggressive. The Python (line 596) has no such guard: if raw_cross and signal_candidate == SIGNAL_NONE: — no check for not use_aggressive. So in AGG_EMA mode the Python will generate backstop signals that the MQL5 never would.

5. Historical spike doesn't set spike_active/spike_bar in Python

In the MQL5 (lines 1806–1809), when CheckSpikeHistorical returns a signal, the code sets g_spikeActive = true and g_spikeBar = iIX so the spike window tracking carries forward. In Python, check_spike_historical returns the signal and price but never mutates state.spike_active or state.spike_bar — the caller doesn't set them either. This means the spike-window expiry logic and all spike-active guards won't function for historical spikes.

6. Provisional signal logic is entirely absent

The MQL5 has a complete provisional-signal mechanism: snapshots of trade/cocked state before a live-bar provisional signal, reversion on invalidation (lines 2071–2082), bar-close commit of provisionals on new bar (lines 1662–1672), and the g_provisionalSignal flag gating whether a signal is committed or tentative. The Python has none of this — no provisional_signal state, no snapshots, no reversion. For offline/historical-only use this is mostly fine (all bars are "closed"), but the isNewBar/isLiveBar semantics that the Python does carry (is_new_bar = True, is_live_bar = (i == live_bar)) interact incorrectly with the missing provisional logic: the last bar will be treated as live, and without provisional handling its signal behavior diverges.

7. condition_met referenced before assignment in non-aggressive provisional check

At Python line 546, signal_candidate == SIGNAL_NONE falls through to the aggressive cocked-trigger block which only sets condition_met if state.is_cocked is true. But later at line 596 (backstop) and the implicit fall-through, condition_met is referenced in the provisional management that the MQL5 has (though Python omits it). If this code were ported more completely, condition_met would blow up as uninitialized when use_aggressive is true but is_cocked is false.

8. readout_to_price is hardcoded to price-mode only

The Python readout_to_price (line 141–142) is a passthrough (return value). That's correct only when InpReadoutUnits == READOUT_UNITS_PRICE. If someone runs with pip-mode readout units, the sensitivity/flat-slope conversion would be wrong. Minor — the default params match price mode — but it's a silent assumption.

9. Cross-after-signal reset condition differs

The MQL5 (line 2412) does the cross-after-signal reset regardless of whether a signal fired on the current bar — it runs after the signal-commit block. The Python (line 705) adds and signal == SIGNAL_NONE as an extra guard, which means a bar that both fires a signal and has a qualified cross won't do the reset that the MQL5 would do. (In the MQL5 the reset runs and then continue skips the rest of the loop — so the signal commit already happened, and the reset just cleans up state for the next bar.)

In summary: the core TEMA/EMA cross detection, T2E sign logic, KC computation, spike-historical geometry, and aggressive trigger-condition math are all faithful ports. The divergences are in control flow ordering (cocking placement), missing guards (!g_spikeActive on several blocks, !isAggressive on backstop), missing provisional-signal handling, and missing state updates after historical spike detection. Of these, the cocking-order and backstop-in-aggressive-mode issues will produce different signal sequences even on purely historical data.
