2. Is this code way more complicated and unstructured than it needs to be?

Yes. Hard yes. Concrete evidence:

  • Three independently-tracked "pending signal" mechanisms that partially overlap: trigger_pending (non-aggressive delayed cumulative-spread trigger), blackout_signal_pending (signal stored until blackout ends), and aggr_flip_check_pending (scheduled re-check of aggressive signal direction). Each has its own bar index, direction, and clear/cancel rules. They don't share a data structure.
  • A provisional-signal/snapshot system that is entirely vestigial. snapshot_trade_dir, snapshot_is_cocked, snapshot_cocked_dir, snapshot_cock_level, revert_provisional_signal(), and the entire not is_new_bar branch exist to support a live-bar-revertible signal model. is_new_bar is hard-coded True, so none of it runs. But it still participates in the control flow — lines 1538–1547 still check state.provisional_signal on every bar, line 1670–1676 still checks for revert conditions. Dead weight that the reader still has to trace to be sure it's dead.
  • A parallel pre-spike snapshot system (17 pre_spike_* fields on State, snapshot_pre_spike_state(), restore_pre_spike_state()) that does something real but is implemented as hand-copied field-by-field assignment when a single dataclasses.replace or copy.copy would do it in one line.
  • State object with 50+ fields, many of which are partially-initialized "book-keeping" that is set but not read (pending_confirm, extreme_open_ref_bar in some paths, spike_pre_spurt_extremum outside its one user), and flags that shadow each other (aggr_recovery_active never persists, reverted_mode is aggressive-only but checked in non-aggressive paths).
  • detect_signals is a 400+ line loop body with at least eight distinct responsibilities interleaved: spike handling, cocking, raw-cross tracking, aggressive entry, non-aggressive trigger arming, non-aggressive trigger firing, backstop, blackout management, flip-check, signal commitment, pricing, cycle reset. There is no subroutine boundary between any of them. You cannot read one without holding the state of all the others.
  • Bandaids visible in the source. Line 1393 resets spike state by a bar-distance check; line 1398–1401 then checks spike reset again via a different mechanism (check_spike_reset by price) before possibly starting a new spike. Two exit rules for the same state. The redundant aggr_recovery_active = True; aggr_recovery_active = False at 1657–1660 is the clearest fossil of "I needed this to fire sometimes but then it broke X so I undid it."

The structural smell is: every single feature was added by extending State, adding a new pending-flag, and wedging a new branch into the main loop rather than by refactoring. That's exactly the Rube Goldberg pattern you named.

3. Could a much cleaner, straightforward, maintainable .py be written that achieves the same results / same output without the confused logic?

Yes — with one important caveat about what "same results" means.

Clean equivalent: absolutely achievable. The actual live logic, once you strip the dead code, reduces to roughly:

  • precompute MA1, MA2, KC bands, EMA2_HLCC4, dyn_blackout, width_ratio, mid_slope per bar (pure vectorized pass, no loop)
  • single loop over bars. Per bar: detect raw cross → update cycle direction if unset → attempt to cock from last 1–2 bars → in aggressive mode, if cocked and close clears MA2 + sens + optional gates, emit; in non-aggressive mode, if cocked and raw cross same-direction, arm a delayed trigger that fires when cumulative |MA1−MA2| reaches sens; spike detection as an orthogonal module with its own clean start/update/exit; one unified "pending signal" queue with a single cancel rule (spread retraced) and a single fire rule (blackout expired + inside window); commit → reset cycle.
  • one table of exit rules, each a small function of (entry, bars, series) → Optional[(bar, price, reason)]; choose_earliest on the list.

That's a few hundred lines, not 2,040. State collapses to maybe 12 fields. The main loop becomes readable top-to-bottom. The dead branches disappear because there's no live-bar/new-bar distinction to carry — you just process completed bars, which is what the current code actually does anyway.

The caveat you need to accept up front: if "same results" means byte-identical signal and trade CSVs on your existing data, you cannot remove the bugs and keep the output. The aggr_recovery_active flip-flop at 1657–1660, the dead provisional_signal branches, the unused pip_size conversion, the ignored use_csv_indicator_columns flag, and the dead spike pause-ms exit are all currently part of the output-producing behavior in the sense that they don't produce anything, but the code's other paths were tuned around them being inert. Removing them doesn't change outputs. But the hybrid pending-signal machinery is more tangled — for example, collapsing trigger_pending + blackout_signal_pending into one queue requires care around ordering, because the current code checks them in a specific sequence that has load-bearing side effects (backstop clears trigger_pending; flip-check clears both; etc.). A faithful clean rewrite has to preserve that ordering or the signals shift.

So: a clean rewrite that is behaviorally equivalent on your test set to within rounding is very reasonable. A clean rewrite that is bit-for-bit identical on every edge case is possible but requires locking the rewrite against your current CSV outputs as a regression test — which you'd want anyway before porting anything new to MQL5.

My recommendation, if you want to go this route: keep the current file as the oracle, write a clean replacement, run both on the same input, diff the signal and trade CSVs bar-by-bar, and only accept the rewrite when the diffs are either empty or explicable (e.g., rounding at the 4th decimal of effective_trigger_sens). That's the same discipline you already use for the MQL5 ports.

One thing to watch on first compile: MQL5's FileWrite with FILE_CSV uses a tab delimiter by default unless you specify the delimiter in FileOpen. I specified ',' as the delimiter in both FileOpen calls — confirm the output CSVs are comma-separated when you open them. If MT5 ignores the delimiter argument in FILE_CSV mode on your build, swap to FILE_TXT and write the commas manually. Tell me if that happens.
