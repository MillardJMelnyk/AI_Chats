MILLARD2026-07-13 16:31 UTC

Here are a bunch of MQL5 functions, etc., that I want ported to C#/cTrader. I want them available to call like you would a function in a DLL (or whatever the correct terminology is.) What are the options?

CLAUDE2026-07-13 16:31 UTC

Three options, best first:

  1. .NET class library (DLL) — port the code to a plain C# class library, compile it, and reference the DLL from any cTrader indicator or cBot. This is the direct equivalent of what you described: call the functions like library functions. cTrader (cAlgo) supports referencing custom .NET assemblies.

  2. cTrader custom indicator — port each calc as a cTrader Indicator, then other indicators/cBots pull its output buffers via cTrader's built-in indicator-reference mechanism. More cTrader-idiomatic, but you call buffers, not functions.

  3. Shared source files — keep the ported code as .cs files added to each cBot/indicator project. No DLL, simplest to iterate on, but no single compiled unit.

Option 1 matches your ask. Want me to look at the three files and propose a port plan?

MILLARD2026-07-13 16:32 UTC

Between # and #2, what's the performance tradeoff?

CLAUDE2026-07-13 16:32 UTC

No real difference. Both compile to .NET code running in the same process. The DLL is called directly, so it's marginally faster than reading another indicator's buffers through cTrader's indicator-reference layer, but on tick-level workloads the difference is negligible — not something you'd see in dollars and cents. Pick on architecture, not speed.

MILLARD2026-07-13 16:32 UTC

OK, pros/cons architecturally, STE

CLAUDE2026-07-13 16:33 UTC

DLL (option 1):
- Pro: One copy of the logic, everything calls it directly, same shape as your MQL5 include files.
- Pro: You control state and calibration objects yourself — no framework in the way.
- Con: You compile it separately in Visual Studio; a change means recompile, drop new DLL in, restart cTrader stuff using it.
- Con: cTrader debugger doesn't step into it easily.

Custom indicator (option 2):
- Pro: Edit and compile inside cTrader, no outside tools.
- Pro: Output shows on chart for free.
- Con: You get buffers, not function calls — awkward for things like your calibrator/detector classes that hold state and answer questions on demand.
- Con: Each consumer spins up its own copy of the indicator — duplicate state, duplicate work.

Your code is stateful classes, not line buffers. DLL fits.

MILLARD2026-07-13 16:35 UTC

any merit to devo/test as #2, once humming, convert to #1, or is that a wash?

CLAUDE2026-07-13 16:35 UTC

Wash, mostly. The port work is the same either way; wrapping it as an indicator versus a DLL is thin packaging around the same classes. The "test as indicator" benefit is seeing output on the chart — but you can get that from a DLL too by writing a small throwaway indicator that calls it and plots. Going #2 first means writing indicator plumbing you'll later throw away, and it pushes you toward buffer-shaped code that fits your classes badly.

Cleaner path: port straight to a class library, then build one thin cTrader indicator that calls it for visual checking. That gives you the #2 benefit without the rework.

Same pattern works, just two deploy targets instead of one.

Layout:
- Keep your VS Code workspace as the master source, same as now — one folder for the class library (.cs files), one for the thin cTrader indicators/cBots that call it.
- cTrader's live locations: source files for indicators/cBots live in Documents\cAlgo\Sources\Indicators and ...\Sources\Robots. Your compiled DLL goes wherever you like; each cTrader project just references it by path.

Deploy flow, two stages:
1. DLL stage: AI edits library code in the workspace → you build the DLL (one command: dotnet build, no Visual Studio needed) → your compare utility copies the new DLL to the live folder, archiving the old one with timestamp first, exactly like your MQ5 flow.
2. Indicator/cBot stage: same compare utility, second target: workspace .cs file → Documents\cAlgo\Sources\..., archive old copy first. Then recompile inside cTrader (their equivalent of your F7).

So the only new moving part is the dotnet build step for the DLL. Your existing archive-before-replace utility just gets a second set of source/target path pairs. No git needed — the same crude-but-working scheme carries over intact.

One warning: cTrader locks the DLL while a chart is using it, so the copy step fails unless the indicator/cBot is removed or cTrader closed first. Build that check into the utility or you'll chase phantom "file in use" errors.
