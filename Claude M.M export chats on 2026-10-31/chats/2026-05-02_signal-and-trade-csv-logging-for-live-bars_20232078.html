I have enough. Here's the diagnosis and the fix.

What's broken

Three independent defects, all in the CSV write path. Any one of them alone breaks live logging; together they guarantee nothing useful ever lands on disk.

Defect 1 — WriteOutputCSVs is gated on prev_calculated == 0 (line 3587)

if(prev_calculated == 0 && !g_csv_outputs_written)

Live ticks always have prev_calculated != 0, so the call from line 6301 only writes during the initial full pass. Live signals/trades cached after that never get flushed.

Defect 2 — Cache arrays are wiped on every full-pass entry (lines 4917–4923)

if(write_output_csvs)
{
   ArrayResize(g_csv_signals, rates_total);
   g_csv_sig_count = 0;
   ArrayResize(g_csv_trades, rates_total);
   g_csv_trade_count = 0;
}

Anything cached in a prior pass is erased before the next pass starts. Combined with Defect 1, even if the gate were relaxed the cache would be empty by the time history was rewritten.

Defect 3 — The signal_start >= rates_total early-exit branch never logs anything (lines 4892–4915)
The branch returns without ever calling WriteOutputCSVs and without recording anything about the early-exit condition itself. The "ON_CALCULATE_EARLY_EXIT" debug write goes to the debug log, not the signal/trade CSVs.

The fix

Stop caching-then-flushing. Open both CSV files once with headers, then append each row immediately when it is emitted. Close them in OnDeinit.

Concretely:

1. Replace g_csv_signals[] / g_csv_trades[] with two persistent file handles

int  g_signal_fh = INVALID_HANDLE;
int  g_trade_fh  = INVALID_HANDLE;
bool g_csv_headers_written = false;

2. New OpenOutputCSVs() called once from OnInit (or lazily on first emit)
- Opens both files with FILE_WRITE|FILE_READ|FILE_CSV|FILE_ANSI|FILE_SHARE_READ
- Uses FileSeek(fh, 0, SEEK_END) so reopens append rather than truncate (matters for restarts mid-session)
- Writes the header row only when g_csv_headers_written == false AND the file is empty (FileSize(fh) == 0)
- FileFlush after the header

3. New AppendSignalRow(...) and AppendTradeRow(...)
- Same field layout as the current CSV_WriteSignalCSV / CSV_WriteTradeCSV loop bodies
- Call FileFlush(fh) after every FileWrite so a crash/disconnect doesn't lose the row
- These replace CacheCSVSignalRow and CacheCSVTradeRow at every call site (the two CacheCSVSignalRow / CacheCSVTradeRow invocations around lines 5303 and 6126/6136)

4. Delete the cache-wipe block at lines 4917–4923 entirely.

5. Delete WriteOutputCSVs and its call at line 6301. No batched write exists anymore.

6. Log the early-exit branch as well. Before the return rates_total at line 4914, emit a synthetic row to the signal CSV (or to a third early_exits.csv if you want it segregated) capturing signal_start, rates_total, live_bar, live_time, g_chart_signal_start, g_trade_start, prev_calculated. This is the data Sonnet's "early exit" path currently throws away.

7. OnDeinit closes the handles

if(g_signal_fh != INVALID_HANDLE) { FileClose(g_signal_fh); g_signal_fh = INVALID_HANDLE; }
if(g_trade_fh  != INVALID_HANDLE) { FileClose(g_trade_fh);  g_trade_fh  = INVALID_HANDLE; }

And remove g_csv_outputs_written — it's meaningless once writes are streamed.

Net effect

  • Historical pass: each signal/trade is appended the moment it's emitted inside the signal_start … rates_total loop.
  • Live ticks: same code path, same append, no gating on prev_calculated.
  • Early-exit branch: writes a diagnostic row before returning.
  • Crash mid-run: everything up to the last FileFlush is on disk.

No, that's not what happens. Here's the actual layout:

Signal CSV — one row per:
- Each signal fired (line 6211)
- Each early exit (line 4993)

Trade CSV — one row per closed trade only. A row is written when:
- An exit fires on its own (stop/take-profit/etc.) — line 5389
- A new opposing signal fires and closes the prior open trade — line 6220

No row is written when a trade is entered. A trade entry only generates a signal row. The trade only gets a CSV row once it closes — and the closing row contains the entry data plus the exit data together.

So if a signal fires and opens a trade, you get:
- 1 signal row immediately
- 0 trade rows (the trade is open, not yet closed)

When that trade later closes:
- 0 or 1 signal rows (1 only if the close was triggered by a new opposing signal)
- 1 trade row

This matches the original design's intent — TradeRow has both entry and exit fields populated together, so it can only be written at close time.

If you want a row per entry (open trade) too, that's a separate change.
