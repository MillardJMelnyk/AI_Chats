Unified warm-up control and start time handling

MILLARD2026-07-11 13:03 UTC

Is this change plan correct and will it result in the indy handling start times and warm up start times proplerly?

Change plan

  1. Add one shared warm-up control function.
    * LIVE and CSV main logic will only call this function.
    * No warm-up dates, mode decisions, checks, start-line work, prints, or stopping decisions will remain inline.
  2. The shared function will determine:
    * Indy warm-up start datetime.
    * Ratio warm-up start datetime.
    * Start line datetime.
    * Whether both warm-ups have sufficient data.
    * Whether to proceed, wait for more CSV data, or stop with an error.
  3. Date range on, LIVE or CSV:
    * Start line datetime = InpProcessStartDateTime.
    * Calculate each warm-up start datetime backward from the start line datetime.
    * Use actual existing bars when counting backward.
    * CSV will read and process rows needed before the start line instead of skipping those warm-up rows.
  4. Date range off, LIVE:
    * Start line datetime = current tick datetime.
    * Calculate each warm-up start datetime backward from that datetime.
    * Load and check the required terminal history.
  5. Date range off, CSV:
    * Begin both warm-ups at the first replayed CSV tick.
    * Work forward through the CSV.
    * The first tick where both warm-ups are complete becomes the start line datetime.
    * No backward CSV calculation will be used.
  6. Keep the two warm-ups separate.
    * Indy warm-up must prove the indy lines, slopes, and spreads are ready.
    * Ratio warm-up must prove the ratios and ratio slopes are ready.
    * One warm-up completing will not stand in for the other.
  7. Check data sufficiency in both modes.
    * Date range on: data must reach both calculated warm-up start datetimes.
    * LIVE with date range off: terminal history must reach both calculated warm-up start datetimes.
    * CSV with date range off: the file must continue until both warm-ups complete.
    * CSV ending before both complete will be an error.
  8. On insufficient data, print:
    * Feed mode.
    * Start line datetime.
    * Required Indy warm-up start datetime.
    * Required ratio warm-up start datetime.
    * Actual available data start and end datetimes.
    * Which warm-up failed.
    * Then stop the run.
  9. On sufficient data:
    * Complete both warm-ups.
    * Plant the start line.
    * Print the same warm-up and start-line information in LIVE and CSV.
    * Allow signal detection and trading only from the start line datetime.
  10. Remove the present CSV warm-up bypasses and the separate combined-history shortcut.
  11. Do not change signal rules, trade rules, CSV columns, DLOG columns, replay chunking, or buffer meanings.
  12. Update both changed file headers and raise PROGRAM_VERSION from 1.69 to 1.70.
  13. Verify all six cases:
    * LIVE, date range on, sufficient data.
    * LIVE, date range on, insufficient data.
    * LIVE, date range off.
    * CSV, date range on, sufficient data.
    * CSV, date range on, insufficient data.
    * CSV, date range off, both sufficient and insufficient endings.
CLAUDE2026-07-11 13:06 UTC

No — not as written. The plan matches the code's structure, but four gaps will stop it from producing correct start times:

  1. The indy warm-up has no defined length. Right now the indy lines are simply computed over every bar on the chart; nowhere in the file is there a required indy bar count. The shared function cannot calculate an "indy warm-up start datetime" backward until you first decide how many bars the indy lines need to be considered ready. The plan assumes that number exists. It doesn't. This must be ruled on before the plan can work.

  2. LIVE and CSV build the indy lines from different data. LIVE builds them from chart bars; CSV replay builds them from the replayed ticks (the code says so explicitly, and CSV mode never runs the bar-based indy pass). One shared function must judge indy readiness two different ways, and the plan doesn't say how. Point 6 ("Indy warm-up must prove the indy lines are ready") is stated as one rule, but it's two different proofs.

  3. CSV sufficiency also depends on chart bars, not just CSV rows. Replayed ticks land on chart bars; any tick older than the chart's first bar is dropped. A CSV file that reaches back far enough will still fail if the chart doesn't cover those dates. The plan's sufficiency check (point 7) looks only at the file.

  4. LIVE with date range off has no "wait" outcome. Point 2 allows proceed, wait-for-CSV, or stop. If terminal tick history doesn't reach the calculated warm-up starts, point 8 says stop the run — where the current build keeps gathering ticks forward with a progress meter. If stop-on-error is what you want there, fine, but the plan changes that behavior without saying so.

One thing I can't verify: the CSV row skipping, the replay feed, and the row filtering all live in the CsvTickFeed include files, which weren't uploaded — so points 3, 5, 7, and 10 of the plan can't be checked against actual code from here. Point 12 says "both changed file headers"; there are five CSV include files, so which second file changes is also unconfirmed.

What checks out: the version is 1.69 as stated; the CSV bypasses named in point 10 exist exactly as described (CSV never sets the warm-up-complete latch, and CSV signal start uses a single combined tick-history check standing in for both warm-ups); and points 3–5's start-line definitions are consistent with the existing window logic.
