MILLARD2026-07-13 16:07 UTC

I need a better understanding of how indicator and bot code is handled in cTrader. MQL5 uses #include modules for general-purpose/shared functions.

CLAUDE2026-07-13 16:07 UTC

cTrader uses C# instead of a scripting language, so shared code works the way it does in any C# project — no #include. Three ways to share code:

  1. Same-file or partial classes — simplest, but not really shared across bots.
  2. Referenced .NET class library (DLL) — you build a normal C# library project with your shared functions, then reference it from any indicator or cBot. This is the direct equivalent of your _MJM.mqh modules, except compiled separately.
  3. Referencing another indicator/cBot's source — cTrader lets an indicator or bot reference another cTrader algo project directly (in the modern cTrader editor or Visual Studio), so you can keep a "library" algo holding common classes.

Since cTrader 4.x everything compiles to .NET (currently .NET 6+), and you can develop entirely in Visual Studio with full solution/project structure, NuGet packages, and a real debugger — a big step up from MetaEditor. Indicators inherit from Indicator, bots from Robot, and calling an indicator from a bot is done with Indicators.GetIndicator<MyIndicator>(...) rather than iCustom handles.

One practical difference that matters for your TTEM-style work: cTrader gives cleaner tick access (OnTick, MarketData, Bars objects) and backtesting with real tick data built in, but there's no direct equivalent of MQL5's buffer-index model — indicator outputs are IndicatorDataSeries you read by bar index, forward-indexed like you already prefer.

MILLARD2026-07-13 16:09 UTC

2 is about using compiled code, #3 about common authority on the source code?

CLAUDE2026-07-13 16:09 UTC

Roughly, yes. #2: shared code lives in a separate library, you reference the compiled DLL — consumers don't see or rebuild the source. #3: the shared code is itself a cTrader algo project (source), and other algos reference that project; changes to the source flow into everything that references it on rebuild, so the source stays the single authority. Under the hood #3 still compiles to an assembly, but you're maintaining one live source instead of distributing a binary.

MILLARD2026-07-13 16:10 UTC

So #3 ~ #include

CLAUDE2026-07-13 16:10 UTC

Yes — functionally closest to #include: one shared source, every consumer picks up edits on rebuild. The mechanical difference is it's a project reference (compiled as its own assembly), not textual pasting, so no include-guard or duplicate-definition issues.

MILLARD2026-07-13 16:11 UTC

So doe cTrader have its own code editor?

CLAUDE2026-07-13 16:11 UTC

Yes. cTrader has a built-in code editor (the "Automate" section, formerly cAlgo) where you write, compile, and run indicators/cBots directly. It's fairly basic — syntax highlighting, IntelliSense-style completion, one-click build. For anything serious you can open the same project in Visual Studio or VS Code straight from cTrader; since it's standard C#/.NET, you get full tooling, debugging with breakpoints, and Git.

MILLARD2026-07-13 16:17 UTC

I'm very familiar with MQL5 indicators and how they work. Briefly STE explain how indys work in cTrader, what their basic structure is, and how they interact with the platform (counterpart to indy/terminal interaction in MQL5).

CLAUDE2026-07-13 16:17 UTC

A cTrader indicator is a C# class inheriting from Indicator. Two methods do the work: Initialize() (counterpart of OnInit) runs once, and Calculate(int index) (counterpart of OnCalculate) which the platform calls per bar — but one bar at a time: on load it calls it for every historical bar in order, then on each new tick it calls it again for the current bar. You never write the history loop yourself; the platform owns the loop and hands you the index.

Outputs are IndicatorDataSeries declared with an [Output] attribute — counterpart of indicator buffers with plot properties set by attributes instead of #property lines. You just assign Result[index] = value inside Calculate. Inputs are properties with a [Parameter] attribute — counterpart of input variables.

Platform interaction: everything comes through inherited objects instead of function calls. Bars gives OHLC/time series, Symbol gives instrument info, Chart gives chart drawing, MarketData gives ticks and other timeframes. Indexing is forward (0 = oldest), no series arrays. Repainting the current bar happens naturally because Calculate re-fires on every tick for the last index; historical bars stay put unless you write to them.
