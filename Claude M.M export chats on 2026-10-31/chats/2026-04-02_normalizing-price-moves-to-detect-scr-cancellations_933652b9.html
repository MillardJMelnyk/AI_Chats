1. Best method of the four

The four cancellation approaches are:

Old (raw ratio): current_cbs / previous_cbs — directly compares the developing reversal to the prior completed leg in raw price units. This is the core problem: a $30 prior leg with a $10 reversal gives 0.33, failing a 0.50 threshold, even though $10 is a perfectly meaningful reversal in absolute terms.

Zscore (population): Converts both magnitudes to CDF percentiles via (value - mean) / stddev → normal_cdf(). Sensitive to outliers pulling mean and stddev around. A single spike leg can inflate stddev and compress everything else toward 0.5. Also, because you're feeding absolute magnitudes (always positive) through a normal CDF, you're effectively only using the right half of the distribution — the mapping is monotonic but wastefully compressed.

Percentile (population): Pure empirical rank. Both magnitudes get mapped to their position in the sorted population. No distributional assumptions, no outlier sensitivity. A $10 reversal that's at the 60th percentile against a $30 prior leg at the 95th percentile gives cancel_pct = 0.60/0.95 ≈ 0.63 — passes. This is exactly the normalization behavior you want: "how big is this move relative to what moves normally look like?"

Robust zscore (population): Median/MAD based, then through normal CDF. Better than vanilla zscore against outliers, but still imposes a distributional shape assumption. For leg magnitudes in XAUUSD (which tend to be right-skewed — lots of small legs, occasional huge ones), forcing a Gaussian mapping distorts the tails. In practice it'll behave similarly to percentile but with more complexity and less transparency.

Winner: percentile. It directly solves the stated problem — large prior legs no longer suppress detection of meaningful reversals — with no distributional assumptions, no outlier sensitivity, and the easiest interpretability. The score ratio literally means "the reversal is this fraction as unusual as the prior leg was."

2. Bugs found

Bug 1 — CRollingPopulation.add() removal logic (line 84-86). When evicting the oldest value, bisect_left finds the insertion point for oldest in sorted_values. If there are duplicate values and bisect_left lands on a different copy than the one being evicted, that's actually fine — any copy of the same value is equivalent. However, the guard if remove_ix < len(self.sorted_values) silently skips removal if bisect_left returns an index equal to the length. That can only happen if oldest is greater than every element in sorted_values, which shouldn't occur since oldest was added to it. But the real bug is subtler: floating-point drift in sum_values and sum_squares from repeated add/subtract cycles. Over a long M1 dataset these accumulators will drift, potentially making variance go slightly negative (the max(variance, 0.0) on line 109 is already a band-aid for this). This won't crash but will degrade zscore accuracy over time. Percentile is immune to this since it only uses sorted_values.

Bug 2 — held_completed_leg_mag is computed but the first completed leg is never added to the population. Walk through it: when pivot_bars first reaches length 2, held_completed_leg_mag gets set (line 235). But that value only gets population.add()'d on the next pivot detection (line 225-226). So the population always trails by one leg. More importantly, on the very first pivot (pivot_bars going from 0 to 1), held_completed_leg_mag is still None, so nothing is added. Then on the second pivot (pivot_bars going to length 2), held_completed_leg_mag is None so nothing is added, but it gets set. Then on the third pivot, the leg from pivot 1→2 finally enters the population. This means the first completed leg (pivot 0→1) is permanently lost — it never enters the population at all. For a min_population of 20 this is minor, but it's still structurally wrong.

Bug 3 — Population contains TEMA-slope-detected leg magnitudes, but the CBS magnitudes being scored against it are close[pivot] - open[prev_pivot]. These are different measurements. The TEMA slope legs are measured as close[curr_pivot] - open_[prev_pivot] (same formula), so they do match. This is actually fine — I initially thought the ZZ legs were being mixed in, but they're not. No bug here on second look.

Bug 4 — In the spread-alignment step (lines 260-311), the continue statements on lines 266, 269, and 271 skip the entire rest of the loop iteration. This means if CBS direction flips (e.g., price crossed back through the pivot open), the candidate is preserved and checked again next bar — that's intentional. But if current_cbs == 0.0 (line 265), the continue also skips Step 4 (the if current_scr is not None block on line 313). Since current_scr is initialized to None at the top of the loop and isn't set before this point, that's harmless. No functional bug, but worth noting the continue is heavier than it needs to be.

Bug 5 — Old method detect_scrs (phase4 file): cancel_pct is a signed ratio. Line 175: cancel_pct = current_cbs / previous_cbs. For a true cancellation (opposite direction), this will be negative. Then line 176 checks cancel_pct >= 0.0 to skip same-direction cases. Line 178 checks abs(cancel_pct) >= min_cancel_pct. This works correctly — negative ratio means opposite direction, and abs() gets the magnitude. But note: the ratio is asymmetric. If the prior leg was short (negative previous_cbs) and the reversal is long (positive current_cbs), you get a negative ratio whose magnitude is |current/previous|. A $10 reversal against a $30 prior gives |10/30| = 0.33. A $10 reversal against a $3 prior gives |10/3| = 3.33. So the raw ratio also breaks in the other direction — tiny prior legs make everything look like a massive cancellation. The population methods fix this too, since both get scored against the same distribution.

Bug 6 — scr_start_dt inconsistency. In the old method (line 193), scr_start_dt is set to times[i-1] — the confirmation bar. In the population method (line 283), scr_start_dt is set to times[curr_pivot] — the pivot bar. These should be the same across methods for apples-to-apples comparison. Given your earlier work establishing that SCR start datetime should be the detection bar, the population method's use of the pivot bar time is the one that's wrong.

3. Better alternative

The population approach is the right direction. Percentile is the right scoring method. But the architecture has a structural issue: you're scoring the developing reversal bar-by-bar, re-evaluating cancel_pct every bar until it either passes or a new pivot resets everything. This means a reversal that's slowly growing will eventually cross the threshold even if it took 50 bars to get there — at that point the move may no longer be an impulsive cancellation, just a slow grind.

Suggested improvement: add a max-bars-from-pivot constraint. After the CBS candidate is set, require that the spread alignment + cancel_pct threshold be met within N bars of the current pivot. This preserves the "impulsive reversal" character of what you're detecting. You could parameterize it (e.g., --max-confirm-bars 10) and sweep it alongside the other parameters.

Second suggestion: score both legs against the same population snapshot. Right now, prior_score is computed once when the candidate is created, but current_score is re-evaluated every bar as the developing reversal grows. The population itself also grows (new completed legs get added as new pivots form). This means the prior and current scores are measured against slightly different populations if a pivot forms mid-wait. Freezing the population reference at candidate creation time (snapshot the sorted_values list) would make the comparison cleaner. In practice this probably doesn't matter much with a 100-element rolling window, but it's worth being precise about.

Third suggestion: instead of score(current) / score(prior), consider score(current) >= score(prior) * min_cancel_pct. This is algebraically the same but reads more clearly as "the reversal must be at least X% as significant as the prior leg." More importantly, it lets you separately threshold a minimum absolute magnitude for the reversal — e.g., require current_score >= 0.20 regardless of cancel_pct, so you never fire on a reversal that's in the bottom quintile of all moves even if the prior leg was also tiny.
