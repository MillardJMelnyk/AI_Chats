Geometric pattern detection from x,y data — depends on what you mean by "pattern." A few different problem classes, since the right library differs a lot by what you're actually trying to find:

Shape fitting (lines, circles, ellipses, polygons)
- numpy/scipy.optimize — direct least-squares fitting for known shapes (line, circle, conic sections)
- scikit-image — measure.LineModelND, CircleModel, EllipseModel plus built-in RANSAC fitting (measure.ransac) — good if your data is noisy/has outliers
- opencv-python (cv2) — cv2.fitLine, cv2.minEnclosingCircle, cv2.fitEllipse, contour approximation (cv2.approxPolyDP) for corner/vertex reduction

Clustering points into shape candidates
- scikit-learn — DBSCAN, HDBSCAN to group points before fitting shapes to each cluster
- pyclustering — more clustering algorithm variety if sklearn's set isn't enough

Pivot/extrema/zigzag pattern detection (given your trading work, this might be the actual relevant one)
- scipy.signal.find_peaks / argrelextrema — local max/min detection, which is the core primitive under most zigzag implementations
- no mainstream library does "zigzag" as a named function — it's usually hand-rolled on top of find_peaks, which matches what you've already built custom in MQL5/Python

Convex hull / polygon structure
- scipy.spatial.ConvexHull, Delaunay
- shapely — polygon operations, point-in-polygon, intersection logic once you have geometric primitives

Template/shape matching against a known pattern
- opencv-python — cv2.matchShapes (Hu moments) if you're comparing a point-cloud's shape against a reference
- dtaidistance or tslearn — if "pattern" means a sequence shape over time (e.g., matching a price-curve shape), DTW-based matching is the right tool, not pure geometry

OK, what will it take to port plot_pivots.py into MQL5? I'm not interested in creating the same chart, only in using the same tick pivot detection logic. Can scipy.signal.find_peaks be ported or implemented so that an MQL5 indicator can use it?

CLAUDE2026-06-26 10:49 UTC

find_peaks itself can't be ported — it's a C-extension wrapping a fairly involved algorithm (local maxima detection + prominence calculation via base-level tracing on either side of each peak + neighbor-suppression for the distance constraint). No MQL5 equivalent exists to call into. It has to be reimplemented from scratch in MQL5.

That said, the algorithm itself is fully specified and not large. Here's what porting actually requires:

1. Local maxima/minima pass
Walk the array, find points where price rises then falls (or vice versa for lows). Trivial — same logic as your existing ZigZag candidate-finding.

2. Prominence calculation
This is the part with actual teeth. For each candidate peak, scipy:
- Walks left from the peak until it hits a point higher than the peak (or the array edge)
- Walks right doing the same
- Takes the lower of the two "valley floors" found along those walks
- Prominence = peak height − that floor

This is an O(n) walk per peak in the worst case (though scipy's actual implementation is smarter — it's O(n) total via a stack-based approach, not O(n²)). For an MQL5 indicator running on live ticks, you don't need scipy's optimized version — a straightforward double-walk per candidate is fine unless you're processing huge backfills on every tick.

3. Distance constraint (non-max suppression)
After getting all candidates passing the prominence filter, scipy resolves any pair closer than DISTANCE apart by keeping the higher-prominence one and discarding the other. Simple sort + sweep.

4. Direction-agnostic implementation
Per your conventions — this should be one function taking _dir (+1 for highs, −1 for lows), not two mirrored code paths. Lows = highs run on negated price, which is literally what the Python script already does (find_peaks(-price, ...)), so this maps directly to your existing pattern.

Honest scope assessment: this is a real implementation task, not a one-liner — prominence is the part that's easy to get subtly wrong (off-by-one on the walk boundaries, wrong floor-of-two-sides logic). It's maybe 60-80 lines of careful MQL5 once written, but it needs to be verified against the Python output on the same data before you trust it on live ticks, the same way you bit-verified the Triple_Trigger port.

Want me to draft the MQL5 function now, or do you want to lock the exact prominence/distance semantics first against a few more test slices in Python so the spec is nailed down before it goes into MQL5?

MILLARD2026-06-26 11:09 UTC

So, are there any Python libraries I can use to identify geometric patterns from x,y data in real time, not in arrears?

CLAUDE2026-06-26 11:09 UTC

Short answer: no library does real-time-valid pattern detection out of the box — every named library/function I gave you earlier (find_peaks, RANSAC fitting, ConvexHull, etc.) operates on a static dataset and returns results that are correct only in arrears, because the underlying math (prominence, hull, fit residuals) requires data on both sides of the point being evaluated.

What "real-time" actually changes is not the library, it's how you call it:

  • Sliding/causal window: call the same library (e.g. find_peaks) but only ever pass it data up to index t, never t+1 onward. The function itself doesn't know or care; you're just feeding it a causally-truncated array each time t advances. This gives you the best available estimate at time t, which will be revised as t advances — that's the lag, not a defect.
  • Streaming-specific implementations: a few libraries are designed for online/incremental use rather than batch — e.g. river (online ML, has online change-point/outlier detection), or hand-rolled incremental versions of peak detection that update state per-tick instead of re-scanning an array. These still can't make a point "permanently confirmed" before future data exists — they just avoid re-computing from scratch every tick.
  • Change-point detection libraries (ruptures, or river's online variants) are built around the same in-arrears constraint — offline mode is retrospective, online mode gives a provisional/revisable estimate at each step, same tradeoff as above.

There's no library that defeats the physics: any "is this a peak" answer that depends on prominence (excursion away from the point) cannot be known until that excursion happens. That's true whether it's scipy, river, or hand-rolled MQL5. The only lever is how much you're willing to act on a provisional/revisable estimate vs. wait for a stable one — that's a strategy decision, not a library choice.

Pseudocode for what find_peaks does, restated as the prominence-based pivot algorithm — direction-agnostic per your conventions (dir = +1 for highs, dir = -1 for lows; lows = highs run on negated price):

function find_pivots(price[], prominence_min, distance_min, dir):

    working = price * dir          // dir=+1 for highs, dir=-1 for lows (negation)

    // STEP 1: find local maxima candidates
    candidates = []
    for i from 1 to length(working) - 2:
        if working[i] > working[i-1] and working[i] > working[i+1]:
            candidates.add(i)
        // (flat-top handling: if working[i] == working[i+1] == ... == working[i+k]
        //  and that whole flat run is higher than both neighbors, the run counts
        //  as one candidate — pick its midpoint)

    // STEP 2: compute prominence for each candidate
    confirmed = []
    for each candidate i in candidates:

        // walk LEFT from i until hitting a point higher than working[i], or array start
        left_floor = working[i]
        j = i - 1
        while j >= 0 and working[j] < working[i]:
            left_floor = min(left_floor, working[j])
            j = j - 1

        // walk RIGHT from i until hitting a point higher than working[i], or array end
        right_floor = working[i]
        j = i + 1
        while j < length(working) and working[j] < working[i]:
            right_floor = min(right_floor, working[j])
            j = j + 1

        // prominence = how far the peak stands above the higher of the two floors
        prominence = working[i] - max(left_floor, right_floor)

        if prominence >= prominence_min:
            confirmed.add(i)

    // STEP 3: enforce minimum distance between confirmed pivots
    confirmed = sort(confirmed)
    final_pivots = []
    for each candidate i in confirmed, in order:
        if final_pivots is empty or (i - final_pivots.last) >= distance_min:
            final_pivots.add(i)
        else:
            // too close to previous pivot — keep whichever has higher prominence
            if prominence(i) > prominence(final_pivots.last):
                replace final_pivots.last with i

    return final_pivots, [price[i] for i in final_pivots]

Notes on the parts that matter:
- Step 2's right-side walk is exactly the part that can't complete until future data exists — that's the in-arrears constraint from earlier. Left-side is always immediately known.
- Step 3's tie-breaking (keep higher prominence when two candidates are too close) is a simplification of what scipy actually does — close enough for your purposes, but if you want exact scipy-matching behavior at the distance-tiebreak edge cases, that's a separate, more fiddly spec.
- "Pivot" here = index i and price[i]; "confirmed" = the moment Step 2's right-side walk terminates (hits a higher point or runs out of array), which is the causal-delay concept from the chart you already saw.

CLAUDE2026-06-26 15:52 UTC

Causal version changes Step 2's right-side walk and nothing else.

Arrears (what I gave you): the right-side walk runs to completion against the full, already-collected array — it always finds where it stops, because all the data already exists.

Causal: at the moment you're evaluating candidate i, the array only has data up to the current tick t. The right-side walk can only walk as far as t. Two outcomes:

function find_pivots_causal(price[], prominence_min, distance_min, dir, t):
    // same as before, but working[] only contains price[0..t] — nothing beyond t

    working = price[0..t] * dir

    candidates = ... (same as Step 1, run on this truncated array)

    confirmed = []
    for each candidate i in candidates:

        left_floor = ... (same as before — left side is always fully known)

        // RIGHT-SIDE WALK — the only thing that changes
        right_floor = working[i]
        j = i + 1
        right_side_resolved = false
        while j <= t:
            if working[j] > working[i]:
                right_side_resolved = true     // hit a higher point — floor is settled
                break
            right_floor = min(right_floor, working[j])
            j = j + 1

        if not right_side_resolved:
            // ran out of data before finding a higher point —
            // candidate i is NOT YET CONFIRMED. Prominence is only a
            // lower bound so far (could still grow as more ticks arrive,
            // which could only keep right_floor going lower, or get
            // overturned entirely if a higher point eventually shows up)
            continue   // skip — re-check this same candidate at a later t

        prominence = working[i] - max(left_floor, right_floor)
        if prominence >= prominence_min:
            confirmed.add(i)   // CONFIRMED at tick t — this is the entry on your chart

    // Step 3 (distance enforcement) same as before, applied only to confirmed[]

The actual difference, stated plainly: in the arrears version, every candidate gets a final yes/no answer in one pass because the right-side walk always terminates. In the causal version, a candidate can sit in limbo — "maybe a pivot, not yet provable" — for as many ticks as it takes for either (a) a higher point to show up, settling its prominence, or (b) it to get re-evaluated and pass once enough lower ticks have piled up after it.

That limbo period, summed across all candidates, is exactly what produced the 16.6-tick mean / 11-tick median delay numbers in the chart you already saw. define prominence and distance

CLAUDE2026-06-26 15:56 UTC

Prominence — how far a pivot stands above (or below, for a low) the nearest point on each side that's at least as extreme. Concretely: take the candidate point, look backward until you hit a point higher than it (for a high) or lower (for a low) — track the most extreme point passed along the way. Do the same looking forward. Prominence is the candidate's value minus the less-extreme of those two tracked points (the "higher of the two floors," for a high). A small wiggle that gets swallowed by a bigger move right next to it has low prominence — it doesn't stick up far above its surroundings. This stops the algorithm from reporting two pivots for what's really one swing extreme with a tiny notch in it. A few real options, each with a different mechanism:

1. Volatility-relative prominence (ATR-style)
Instead of a fixed $0.80, compute a rolling measure of recent tick-to-tick movement (e.g., average absolute tick delta, or a rolling stdev, over the last N ticks) and set prominence_threshold = k * rolling_volatility. Choppy stretches get a bigger required threshold automatically; quiet/trending stretches get a smaller one. This is the most direct fix for the specific problem you flagged earlier — that $0.80 meant something different in the calm rally vs. the chop.

2. Adaptive threshold by regime
Classify the recent window into a coarse regime (trending vs. ranging — e.g. via a slope or directional-movement measure) and switch between two or more fixed prominence values depending on regime, rather than a continuously-recalculated one. Less smooth than #1, but simpler to reason about and debug — you always know which of N discrete thresholds is active.

3. Decaying/relaxing threshold over time since the last pivot
Start requiring a high prominence right after a pivot confirms (to avoid immediately flip-flopping), then let the required threshold decay the longer price sits without confirming anything new. This directly targets confirmation lag in quiet periods without loosening the bar during active ones.

4. Percentile-based, not magnitude-based
Instead of a dollar threshold at all, require the candidate's excursion to exceed some percentile (e.g., 90th) of all recent excursions in a rolling window. Self-normalizing, no manual dollar tuning, but percentile computation needs a defined window length and gets more expensive to maintain causally tick-by-tick.

5. Two-stage: fast provisional / slow confirmed
Run two thresholds simultaneously — a low one that fires a provisional pivot quickly, and the current $0.80 one that fires a "hardened" confirmation later. You get an early, revisable signal and the trustworthy one, rather than picking one tradeoff point.

Three specs, no code.

Version A — ATR-style (#1)

  • Maintain a rolling window of the last W ticks' absolute tick-to-tick deltas.
  • rolling_vol = average of those deltas (or stdev — pick one), recalculated every tick.
  • prominence_threshold(t) = k * rolling_vol(t), k a tunable multiplier.
  • Pivot confirmation uses whatever prominence_threshold is at the moment of confirmation (not at the moment the pivot occurred) — since that's the only causally available value.
  • Known weakness, stated up front per your objection: rolling_vol is itself lagging (it's an average of past deltas), so it can be high right as price goes quiet, or low right as price starts moving — same complaint you have about ATR generally. Version B — Regime-switch (#2) + decay-since-last-pivot (#3)

  • Classify current regime using a short-lookback directional measure (e.g., net displacement over last M ticks divided by sum of absolute tick deltas over the same window — a "straightness" ratio, not a magnitude measure, so it doesn't inherit ATR's lag problem from rolling volatility).   • Two fixed thresholds: prominence_trend (lower, since trending moves need less confirmation to trust) and prominence_chop (higher, to filter chop noise) — both hand-set constants, not derived from a rolling average.
  • On top of whichever fixed threshold the regime selects: apply a decay — required threshold starts at the regime's full value immediately after a pivot confirms, then linearly (or step-wise) decreases the longer the algorithm goes without confirming a new pivot, down to some floor.
  • Net effect: the regime check sets which baseline applies, decay handles staleness (quiet periods becoming progressively easier to trigger so confirmation doesn't drag forever in a dead market).
  • This avoids rolling-volatility lag entirely — regime classification here is a ratio of already-realized displacement, not a smoothed magnitude average, so it reflects what price just did rather than smoothing it into delay.

  • Maintain a rolling window of the last W confirmed-pivot excursion sizes (not tick deltas — actual past pivot prominences).
