Claude2026-02-10 20:27 UTC

The culprit is this line in your GetMyHandle():

IndicatorRelease(iMyHandle);

ChartIndicatorGet() returns a new handle reference to the indicator. When you immediately call IndicatorRelease(), you return that handle number to the terminal's handle pool.

Sequence:

  1. TEMA OnInit → ChartIndicatorGet() returns 10 → IndicatorRelease(10) returns 10 to pool → you return 10 (now stale)
  2. EMA OnInit → ChartIndicatorGet() returns 10 (recycled from pool) → IndicatorRelease(10) → you return 10 (now stale)
  3. Script runs → ChartIndicatorGet() for TEMA returns 10 (no release) → for EMA returns 11 (next available)

You're returning a handle you've already invalidated. The script shows correct handles because it doesn't release them.

Why did you add that IndicatorRelease() call? If you need the handle for ongoing use, remove it. If you only need it transiently and want to avoid handle leaks, you have a design issue—you can't both release and use the same handle.

Claude2026-02-10 20:30 UTC

You're right, I misread the flow. Retracted.

Revised diagnosis:

Handles are local to each MQL5 program's handle table, not global.

Each indicator/EA/script has its own handle namespace. When TEMA's OnInit calls ChartIndicatorGet(), it gets handle 10 in TEMA's handle table. When EMA's OnInit calls ChartIndicatorGet(), it gets handle 10 in EMA's handle table. These are different handles with the same numeric value because each program's allocation starts from the same base.

When the script runs, it allocates sequentially within its own handle table: first call → 10, second call → 11.

The handle number is an index into the calling program's private handle table, not a system-wide indicator identifier.

What are you actually trying to accomplish by getting "your own handle"? If you need a unique identifier for the indicator instance, the handle isn't reliable for cross-program comparison. The short name + chart ID + subwindow index would be more stable for identification purposes.

Claude2026-02-10 20:43 UTC

Most likely: piecemeal evolution. ChartIndicatorName() was designed for enumeration/display. ChartIndicatorGet() was added later assuming short names would serve as unique keys—a reasonable assumption if developers always include all parameters in the short name.

The flaw: nothing enforces unique short names, and the built-in indicators don't always guarantee uniqueness (two EMAs with identical settings = identical short names).

A ChartIndicatorGetByIndex() would have been trivial to implement and would have closed the gap. Its absence suggests oversight, not intent.
