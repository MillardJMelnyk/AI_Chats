Summary: Signals of MA Slope Indicator

This is a trend reversal signal generator built on top of a Moving Average slope analysis system. Here's the architecture:

Core Concept

The indicator calculates multiple layers of slope analysis from a base indicator (typically an MA) and generates buy/sell signals when specific conditions are met:

  1. Slope — First derivative of the base indicator (rate of change)
  2. Slope of Slope — Second derivative (acceleration/deceleration)
  3. Net Slope — Slope minus Slope-of-Slope (momentum vs acceleration differential)
  4. Sum of Net Slope — Running sum over a configurable period (smoothed momentum signal)

Signal Generation Logic

The indicator watches for two types of trigger events (configurable via sMarkEventType):

  • "P" (Pivot) — Detects when Net Slope or Sum-of-Net-Slope reverses direction
  • "C" (Cross) — Detects when these values cross the zero line

Cautious mode (bCautious = true for MODERATE risk or lower) requires confirmation: Net Slope must trigger first, then Sum-of-Net-Slope must confirm in the same direction before placing a marker.

Aggressive mode places markers on the first signal from either metric.

Additional Filters

  • Price confirmation — Optionally checks if close price has crossed the base indicator value (with a fudge factor), deferring markers if price contradicts the signal
  • Fudge factors — Configurable tolerances for zero-line crosses (Id0PNT_FudgeFctr) and price crossings (IdPriceFudgePct)

Output

  • Arrow markers (up/down) plotted on chart or subwindow
  • Tracks marker P/L by recording entry prices and calculating theoretical profit/loss between direction changes
  • Maintains running P/L buffer
  • Displays current bias ("UP" / "DOWN" / "Sideways") via chart comment

Indicator Handle Support

Supports MA, TEMA, Stochastic, and custom indicators as the base data source through a unified handle system.

That points to a registry pattern. Each indicator type is registered as a class that encapsulates:

  • Display name (for enum/dropdown)
  • Parameter definitions (types, names, defaults)
  • Handle creation logic
  • Which buffer(s) to read

The MT5 constraint: Input parameters are compile-time only. You can't dynamically generate input fields based on selection. So you have two practical options:

Option A: Superset of inputs Define all possible parameters across all registered indicators as inputs. Each indicator class knows which ones it uses and ignores the rest. Downside: cluttered input dialog with irrelevant fields depending on selection.

Option B: Indicator-specific defaults baked in Each registered indicator class contains its own default parameter values. The input dialog only exposes a few universal parameters (period, applied price, etc.), and the class fills in the rest from its internal defaults. Cleaner dialog, but less user control without recompiling.

Option C: Layered approach Common parameters as inputs (period, MA method, applied price). Indicator-specific parameters stored in the registry class as defaults. Power users can override by creating a new registered variant.

Claude2026-01-14 16:31 UTC

1. Indicator Registry A central repository that holds metadata for every available indicator: display name, whether it's built-in or custom, the path (for iCustom), which parameters it uses from the superset, default values for each, and which buffer(s) contain usable output. Populated at EA initialization. Could be hard-coded or loaded from a config file.

2. Indicator Instance Manager Handles the lifecycle of active indicators. Creates handles when the user adds an indicator, stores them with their current parameter values, removes and releases handles when the user removes one. Maintains a collection of currently active indicator instances, each tagged with an ID so the panel and external code can reference them.

3. Parameter Value Container A struct or class that holds the superset of all possible parameter values. When the user configures an indicator, values go into this container. When creating the handle, the indicator's registry entry specifies which fields to pull from the container and pass to iMA, iCustom, etc.

4. Control Panel (GUI) A chart object-based interface using buttons, dropdowns (simulated with clickable lists), and edit fields. Handles OnChartEvent to detect user interaction. Displays the registry's available indicators, shows the relevant parameters for the selected type, lets the user set values, and triggers add/remove actions through the Instance Manager.

5. Command Interface A mechanism for external code to send instructions. Options: named pipes, files in a watched directory, or socket communication. External code writes a command (add indicator X with parameters Y, remove instance Z, query active instances). The EA polls or listens, parses commands, and routes them to the Instance Manager.

6. Data Output Layer Once indicators are running, their buffer data needs to go somewhere useful. Could populate global variables, write to files, or push through the same communication channel back to external code. This layer handles the "what do we do with the indicator values" question.

Order of implementation: Registry and Parameter Container first (data structures), then Instance Manager (core logic), then either Panel or Command Interface depending on priority, then Data Output.

The MqlParam structure:

struct MqlParam
{
   ENUM_DATATYPE    type;           // TYPE_INT, TYPE_DOUBLE, TYPE_STRING, etc.
