Identified Modularization Opportunities

1. Separation of Concerns in DrawEventArrowsAndSimulateTrades

The function currently handles three distinct responsibilities:

Responsibility Lines (approx) Description
Event Detection ~400 Detecting crosses, kisses, hugs for 3 bands
Arrow Drawing ~80 Creating visual chart objects

Recommendation: Split into:

  • DetectPriceEvents() — returns detected events
  • DrawEventArrows() — consumes events, draws arrows
  • Signal generation stays in or near SimulateTrades()

2. Repetitive Band Processing (The Long If Structure)

The main loop (lines 1014–1481) contains nearly identical code blocks repeated 3 times for upper/middle/lower bands. Each block:

  • Detects potential cross (lines ~1037–1059, 1129–1151, 1220–1242)
  • Confirms or rejects cross (lines ~1062–1126, 1154–1217, 1245–1304)
  • Tracks contact for kiss/hug (lines ~1308–1366, 1368–1421, 1423–1480)

Repetition pattern:

Band processing × 3 bands = ~450 lines that could be ~150 lines + parameterization

Recommendation: Create a BandState struct and process all bands in a loop:

struct BandState {
   double         &line[];        // KC_Upper, KC_Middle, or KC_Lower
   PendingCross   pending;
   int            contact_count;
   int            contact_start_bar;
   bool           in_hug;
   string         band_name;      // "upper", "middle", "lower"
   string         cross_up_signal;   // "XUU", "XMU", "XLU"
   string         cross_down_signal; // "XUD", "XMD", "XLD"
   string         kiss_signal;       // "KU", "KM", "KL"
   string         hug_signal;        // "HU", "HM", "HL"
   int            trade_direction_kiss;  // TRADE_SHORT for upper, contextual for middle, TRADE_LONG for lower
};

3. Duplicate Detection Logic

Two separate detection passes exist:

Function Purpose Redundancy
DetectCrossesWithConfirmation (690–817) Statistics counting Duplicates detection logic
DetectKissesAndHugs (823–~965) Statistics counting Duplicates detection logic
DrawEventArrowsAndSimulateTrades (979–1489) Arrows + signals Re-implements same detection

Recommendation: Single-pass detection that:

  1. Populates event records (g_events[])
  2. Updates counters (g_counters)
  3. Subsequent functions consume events for arrows/signals

4. Arrow Creation Functions

Currently 5 similar functions (lines 1596–1700):

  • CreateCrossArrow
  • CreateKissArrow
  • CreateHugArrow
  • CreateTradeEntryArrow
  • CreateTradeExitArrow

Recommendation: Single parameterized CreateArrow() with an ArrowConfig struct, or at minimum extract common ObjectSetInteger calls.

Proposed Refactoring Order

  1. Extract band state into struct — immediate complexity reduction
  2. Parameterize band loop — eliminates ~300 lines of repetition
  3. Unify detection pass — remove redundant DetectCrossesWithConfirmation and DetectKissesAndHugs
  4. Separate arrow drawing — DrawEventArrows(EventRecord &events[]) consumes pre-detected events
  5. Separate signal generation — signals derived from events, not inline with detection
