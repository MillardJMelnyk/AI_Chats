Claude2026-03-17 17:30 UTC

Found it. The bug is in ConvertTimeServerVSLocal, lines 209–213.

static int offsetSec = INT_MAX;

if(offsetSec == INT_MAX)
    offsetSec = (int)(TimeLocal() - TimeCurrent());

The bug: static — the offset is computed exactly once, at the first call, and never again.

The first call to this function happens during the initial full-chart pass through OnCalculate (when prev_calculated == 0). At that exact moment, TimeCurrent() may not reflect a live tick — it returns the last known server time for any Market Watch symbol, which could be stale if the indicator was just loaded, recompiled, or attached before ticks were flowing.

What happened: At initialization, TimeCurrent() was stale — behind the actual server time by enough to flip TimeLocal() - TimeCurrent() from the expected −32,400 (−9h) to a positive value. Since it's static, this wrong positive offset is permanently cached for the entire lifetime of the indicator instance.

You can confirm: restart the indicator during active tick flow and the local time will immediately correct itself — because the static reinitializes to a fresh TimeCurrent().

The fix: Remove static. The computation is two function calls and a subtraction — the performance cost is zero:

datetime ConvertTimeServerVSLocal(datetime givenTime = 0, string requested = "local")
{
    int offsetSec = (int)(TimeLocal() - TimeCurrent());
    ...

If you want to keep lazy-init for performance reasons, at minimum add a staleness guard — don't accept the cached value if TimeCurrent() was zero or suspiciously far from TimeLocal() at the time of capture.

Claude2026-03-17 17:51 UTC

Fair enough. My static analysis was a real latent bug but not the cause of what you were seeing.

The arithmetic issue: TimeLocal() and TimeCurrent() both return datetime, which in MQL5 is ulong (unsigned 64-bit). When local < server (UTC-6 vs UTC+3), TimeLocal() - TimeCurrent() underflows as unsigned arithmetic, producing a huge positive value. Casting the entire result to int with (int)(TimeLocal() - TimeCurrent()) was truncating that wrapped value unpredictably.

Casting TimeCurrent() to int first forces the subtraction into signed integer arithmetic, where a negative offset is representable correctly.

That said — the static is still a live bug. A stale TimeCurrent() at init will permanently poison the cached offset for that indicator instance. It just wasn't the bug you were chasing right now.
