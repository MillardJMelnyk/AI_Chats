The MQL5 language allows you to write and read global variables that are available outside scripts, indicators, and EAs. What values can these variables take?
Claude2026-01-17 02:40 UTC

Friday, January 17, 2025, 2:34 AM UTC

Global variables in MQL5 (accessed via GlobalVariableSet(), GlobalVariableGet(), etc.) can only store double values.

That's the only data type supported for global variables shared across scripts, indicators, and EAs.

Millard2026-01-17 02:40 UTC
How can you do something similar with strings?
Claude2026-01-17 02:41 UTC

Use file operations with the FILE_COMMON flag:

// Write
int handle = FileOpen("shared_data.txt", FILE_WRITE|FILE_TXT|FILE_COMMON);
FileWriteString(handle, "your string data");
FileClose(handle);

// Read
handle = FileOpen("shared_data.txt", FILE_READ|FILE_TXT|FILE_COMMON);
string data = FileReadString(handle);
FileClose(handle);

FILE_COMMON places files in Terminal\Common\Files\, making them accessible to all scripts/indicators/EAs running under that terminal installation.

Alternative: encode strings as numeric sequences and use standard global variables, but file operations are the direct solution.

Millard2026-01-17 02:42 UTC
Is there any other way to store and share data within the MT5 environment?
Claude2026-01-17 02:42 UTC

Custom indicator buffers: Call an indicator from EA/script using iCustom() or create indicator handle. Read its calculated buffer values. One-way: indicator calculates, others read.

Chart objects: Create graphical objects (ObjectCreate()) with text properties (ObjectSetString() for OBJPROP_TEXT, OBJPROP_TOOLTIP, etc.). Any program accessing the same chart can read via ObjectGetString(). Hacky but functional.

SQLite database: Use DatabaseOpen(), DatabaseExecute(), etc. Full database operations. Shared via DATABASE_OPEN_COMMON flag (common folder) or specific file paths.

Resource variables: Embed data at compile time with #resource. Read-only. Good for static shared data like configuration.

Named pipes: Advanced. Use Windows named pipes for inter-process communication. Requires kernel32.dll imports and WinAPI calls.

Chart properties/comments: Comment() or ChartSetString() to store text visible on chart. Other programs read via ChartGetString().

Most practical for dynamic string sharing: files or SQLite database.

Millard2026-01-17 02:45 UTC
So using chart get string and short set stringChartSetString() and ChartGetString() two indicators running on the same chart could both read and write the same
Claude2026-01-17 02:45 UTC

Yes, technically, but with major caveats:

Writable chart string properties:

  • CHART_COMMENT - the main candidate

The problem: Both indicators writing to the same property will overwrite each other. No locking mechanism. If Indicator A writes "DataA" and Indicator B writes "DataB" on the same tick or close timing, one overwrites the other unpredictably.

Race conditions: No guaranteed order of execution between indicators. Read/write timing conflicts are unavoidable.

Use case limitation: Only works if one indicator writes and others only read, OR if you implement a serialization scheme (like JSON/delimited format where each indicator updates only its portion and preserves the rest - fragile).

Reality: Not designed for this. Files or global variables (for doubles) are the proper mechanisms. Chart properties are for display/UI configuration, not inter-program data exchange.

Can it work? Yes, in controlled scenarios with careful design. Should you use it? No, unless files/database/global variables are somehow unavailable.

Millard2026-01-17 02:52 UTC
How are RGB colors designated numerically?
Claude2026-01-17 02:52 UTC

In MQL5:

Format is BGR (Blue-Green-Red), not RGB.

  • Hexadecimal: 0x00BBGGRR
  • Each component: 0-255 (0x00-0xFF)
  • Stored as integer

Examples:

  • Red: 0x0000FF = 255
  • Green: 0x00FF00 = 65280
  • Blue: 0xFF0000 = 16711680
  • White: 0xFFFFFF = 16777215
  • Black: 0x000000 = 0

Construction:

color c = (blue << 16) | (green << 8) | red;

Extraction:

int red   = color & 0xFF;
int green = (color >> 8) & 0xFF;
int blue  = (color >> 16) & 0xFF;

General programming contexts (non-MQL5): Usually RGB order: 0x00RRGGBB or separate R,G,B values.

MQL5 uses BGR specifically.

Millard2026-01-17 02:53 UTC
How many digits is that?
Claude2026-01-17 02:53 UTC

Hexadecimal: 6 digits (after 0x prefix)

Decimal: 1 to 8 digits

  • Minimum: 0 (black) = 1 digit
  • Maximum: 16777215 (white) = 8 digits

If storing as string for chart comment or file: reserve 8 characters for the decimal value to handle all possible colors.

Millard2026-01-17 02:54 UTC
So 16777215 as a string could be successfully interpreted in code as a color?
Claude2026-01-17 02:55 UTC

Yes.

Convert string to integer, then cast to color:

string colorStr = "16777215";
color c = (color)StringToInteger(colorStr);
// c now equals clrWhite (0xFFFFFF)

StringToInteger() parses the decimal string to integer. Cast to color type interprets it as BGR.

Works bidirectionally:

color original = clrRed;
string stored = IntegerToString(original);  // "255"
color restored = (color)StringToInteger(stored);  // 0x0000FF

Valid for any value 0-16777215.

Millard2026-01-17 02:59 UTC
Can the chart comment set by ChartSetString() be positioned anywhere on the chart?
Claude2026-01-17 02:59 UTC

No.

ChartSetString() with CHART_COMMENT places text in a fixed position (upper-left corner of chart).

For arbitrary positioning:

Use text objects instead:

ObjectCreate(0, "MyText", OBJ_LABEL, 0, 0, 0);
ObjectSetString(0, "MyText", OBJPROP_TEXT, "your string");
ObjectSetInteger(0, "MyText", OBJPROP_XDISTANCE, 100);  // X pixels from corner
ObjectSetInteger(0, "MyText", OBJPROP_YDISTANCE, 50);   // Y pixels from corner
ObjectSetInteger(0, "MyText", OBJPROP_CORNER, CORNER_LEFT_UPPER);

Or OBJ_TEXT for time/price coordinate positioning.

Chart comment = fixed location only.

Millard2026-01-17 03:00 UTC
Why couldn't text objects be used to communicate between indicators on a chart?
Claude2026-01-17 03:00 UTC

They can.

I listed them earlier as "Chart objects" - create text objects with ObjectSetString() for OBJPROP_TEXT or OBJPROP_TOOLTIP, read with ObjectGetString().

Advantages over chart comment:

  • Much longer string limits (tens of thousands of characters depending on property)
  • Multiple objects = multiple independent data channels
  • Can hide from view (OBJPROP_TIMEFRAMES = OBJ_NO_PERIODS)

Same core problem: Race conditions. No synchronization/locking. Both indicators writing to same object = overwrites.

Additional issues:

  • Object name collisions (need naming convention)
  • Objects persist after indicator removal unless explicitly deleted
  • Slightly more overhead than chart comment

Conclusion: Text objects work better than chart comment for data sharing (more capacity, multiple channels), but still inferior to files/database for reliability and design intent.

All chart-based methods are workarounds. Files are the proper solution.

Millard2026-01-17 03:02 UTC
In terms of performance, wouldn't text objects incur much less overhead than CRUD operations on files?
Claude2026-01-17 03:02 UTC

Yes.

Text objects are in-memory operations - orders of magnitude faster than disk I/O.

Performance comparison:

  • ObjectSetString() / ObjectGetString(): microseconds, no disk access
  • File operations: milliseconds, disk write/read cycles, even with OS caching

High-frequency scenarios: If indicators exchange data on every tick, file CRUD becomes a bottleneck. Text objects are vastly superior.

Revised assessment:

Text objects are better when:

  • Performance-critical (every tick or near-constant updates)
  • Data fits within object string limits
  • Race conditions manageable (one-writer-multiple-readers, or careful update protocols)

Files are better when:

  • Data too large for object properties
  • Need persistent storage beyond chart session
  • Multiple programs across different charts/symbols need access
  • Transactional integrity required

Practical pattern: Indicator A writes to hidden text object. Indicators B, C, D read from it. Fast, minimal overhead, works well if write frequency is controlled and readers don't modify.

I overstated "files are proper." For inter-indicator communication on same chart with performance priority, text objects are the better choice.

Millard2026-01-17 03:03 UTC
Is there a function that controverse the objects on a chart of a particular type?
Claude2026-01-17 03:03 UTC

Yes.

ObjectsTotal() and ObjectName() with type filtering:

// Count objects of specific type
int count = ObjectsTotal(0, -1, OBJ_LABEL);  // chart_id, window, type

// Iterate through objects of specific type
for(int i = 0; i < count; i++)
{
   string name = ObjectName(0, i, -1, OBJ_LABEL);
   // Process object...
   string text = ObjectGetString(0, name, OBJPROP_TEXT);
}

Parameters:

  • chart_id: 0 for current chart
  • window: -1 for all subwindows, 0 for main chart
  • type: specific object type (OBJ_LABEL, OBJ_TEXT, etc.) or -1 for all types

Object types for text storage:

  • OBJ_LABEL - screen coordinates
  • OBJ_TEXT - price/time coordinates
  • Any object with text properties

Pattern for data exchange: Name objects with prefix convention (e.g., "DATA_field1", "DATA_field2"), iterate with type filter, parse names to identify data channels.

Efficient enumeration built-in.

Millard2026-01-17 03:05 UTC
But if there were a hundred text objects and only five of them had the prefix we wanted, we'd still have to check all 100 or until we found all five, or is there some way to pre-filter it like the function that deletes objects accepts a prefix?
Claude2026-01-17 03:05 UTC

No pre-filtering for enumeration.

ObjectsDeleteAll() accepts prefix parameter:

ObjectsDeleteAll(0, "DATA_", -1, OBJ_LABEL);  // deletes only matching prefix

But ObjectsTotal() and ObjectName() do not support prefix filtering. You must:

  1. Get total count (optionally by type)
  2. Iterate all objects
  3. Manually check name prefix with StringFind() or StringSubstr()
int total = ObjectsTotal(0, -1, OBJ_LABEL);
for(int i = 0; i < total; i++)
{
   string name = ObjectName(0, i, -1, OBJ_LABEL);
   if(StringFind(name, "DATA_") == 0)  // starts with prefix
   {
      // Process matching object
   }
}

Impact: With 100 objects, 5 matching - you scan all 100. Performance hit is negligible (string comparison is fast), but asymmetry exists: deletion supports prefix, enumeration doesn't.

Mitigation: Use distinct object type for your data objects if possible, so type filtering reduces iteration count.

Millard2026-01-17 03:21 UTC
Would the following method solve the simultaneous update problem you mentioned earlier? Each text object would begin with the timestamp down to the microsecond. Each indicator registered to use that text object to share data would be given a sequential number as part of the registration process. So each indicator that can write to that text object will have a built-in lag factor. A function will handle the direct object set string function. The indicator will pass the value to be written plus its lag factor to the function, which will read The time stamp portion of the object, wait as indicated by the lag factor, then write the value with an updated time stamp.
Claude2026-01-17 03:21 UTC

No.

Critical flaws:

  1. No atomicity: Reading timestamp, waiting, then writing are separate operations. Another indicator can write between your read and write. The lag doesn't prevent this - it just delays your attempt.

  2. No locking mechanism: MQL5 has no mutexes, semaphores, or atomic operations. Your function can't guarantee exclusive access during the wait period.

  3. Wait defeats performance: Sequential lag factors (0ms, 10ms, 20ms, 30ms...) mean indicator #10 waits 100ms every write. You've eliminated the performance advantage of text objects over files.

  4. Registration problem: How do indicators get sequential numbers? This requires... a shared data mechanism to coordinate registration. Circular dependency.

  5. Race on timestamp read: Multiple indicators could read the same timestamp simultaneously, each calculate their wait, all write at staggered times - still overwriting each other.

  6. Execution order not guaranteed: MT5 doesn't guarantee indicator execution order. Lag factors assume predictable timing that doesn't exist.

The actual problem: MQL5 provides no synchronization primitives. No amount of timestamp logic or artificial delays solves this without OS-level locking.

Real solutions:

  • Single writer, multiple readers - only one indicator writes, others read
  • Partitioned namespace - each indicator writes to its own object (e.g., "DATA_IND1", "DATA_IND2"), others read all
  • Accept overwrites - design system to be eventually consistent, tolerate lost updates

Timestamps don't create atomicity.
