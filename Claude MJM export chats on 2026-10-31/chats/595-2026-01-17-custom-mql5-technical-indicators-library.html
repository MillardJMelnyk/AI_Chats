Millard2026-01-17 11:46 UTC
what does the demarker indicator tell you
Claude2026-01-17 11:46 UTC

DeMarker measures demand relative to supply by comparing the current bar's high/low to the previous bar's high/low.

Calculation logic:

  • DeMax = (High > PrevHigh) ? High - PrevHigh : 0
  • DeMin = (Low < PrevLow) ? PrevLow - Low : 0
  • DeMarker = SMA(DeMax, N) / (SMA(DeMax, N) + SMA(DeMin, N))

Output range: 0 to 1

Interpretation:

  • Above 0.7: Overbought. Upward price exhaustion likely. Highs are consistently extending but the move may be losing steam.
  • Below 0.3: Oversold. Downward price exhaustion likely. Lows are consistently extending but selling pressure may be waning.
  • Divergence: Price makes new high but DeMarker doesn't → bearish divergence. Price makes new low but DeMarker doesn't → bullish divergence.

What it captures that RSI doesn't: DeMarker focuses exclusively on the bar's range expansion (high-to-high, low-to-low) rather than close-to-close momentum. It's measuring whether price is successfully probing new territory on each bar. A market can close higher repeatedly (bullish RSI) while failing to make higher highs (bearish DeMarker).

Millard2026-01-17 11:48 UTC
use in place of rsi?
Claude2026-01-17 11:48 UTC

Not a direct substitute. They measure different things.

RSI: Close-to-close momentum. How much are closes gaining/losing relative to recent closes?

DeMarker: Range expansion. Are highs/lows extending into new territory?

When they diverge from each other:

  • Strong closes but failing to make new highs → RSI bullish, DeMarker bearish. Often precedes reversal.
  • New highs being made but closes weak → DeMarker bullish, RSI bearish. Wicks/rejections occurring.

Practical difference:

  • RSI triggers on closing strength
  • DeMarker triggers on probing strength

Better approach: Use both. Confluence when they agree. Warning when they disagree.

If forced to pick one: RSI for trend-following systems, DeMarker for exhaustion/reversal detection.

Millard2026-01-17 11:49 UTC
in what cases is rsi more accurate/informative?
Claude2026-01-17 11:49 UTC

RSI stronger when:

  1. Trend continuation setups. RSI pullbacks to 40-50 in uptrends (or 50-60 in downtrends) reliably signal continuation. DeMarker doesn't track this well because range expansion pauses during consolidation even when trend is intact.

  2. Close-driven markets. Instruments where closing price dominates (daily forex, index futures at session end). Institutional flows target closes. RSI captures this; DeMarker sees only wick behavior.

  3. Gap environments. RSI incorporates gaps through close-to-close measurement. DeMarker ignores gaps entirely since it only compares consecutive highs/lows.

  4. Divergence on momentum exhaustion. Classic RSI divergence (price higher, RSI lower) works better when the issue is weakening conviction rather than failed probes. DeMarker divergence signals different failure mode.

  5. Mean reversion in ranging markets. RSI 30/70 bounces in established ranges. DeMarker's 0.3/0.7 levels are less reliable in chop because range expansion/contraction is noisy without trend.

  6. Filtering for entry timing. RSI crossing 50 as trend filter is cleaner than DeMarker 0.5 crosses. The close-based calculation produces less whipsaw.

Bottom line: RSI tells you about conviction (are closes following through). DeMarker tells you about effort (is price attempting new ground). Conviction matters more in most trend and mean-reversion contexts.

What does #ifndef TEXTGVAR_MQH do?
Claude2026-01-17 12:27 UTC

Include guard. Prevents duplicate compilation if the header is included multiple times.

#ifndef TEXTGVAR_MQH   // If TEXTGVAR_MQH is NOT defined...
#define TEXTGVAR_MQH   // ...define it, then compile everything below

// ... code ...

#endif                 // End of conditional block

Second include attempt: TEXTGVAR_MQH already defined → entire block skipped → no redefinition errors.

Millard2026-01-17 12:28 UTC
when does duplicate compilation happen, when multiple identical #include statements are present?
Claude2026-01-17 12:28 UTC

Yes. Two scenarios:

  1. Direct duplicate - Same file included twice in one source
#include "TextGVar.mqh"
#include "TextGVar.mqh"  // Oops
  1. Transitive/indirect - More common
// IndicatorA.mqh
#include "TextGVar.mqh"

// IndicatorB.mqh
#include "TextGVar.mqh"

// Main.mq5
#include "IndicatorA.mqh"
#include "IndicatorB.mqh"  // TextGVar.mqh pulled in twice

Without the guard, compiler sees the same function definitions twice → redefinition error.

MQL5 has no automatic include-once behavior. Each #include literally pastes the file contents at that location. No guard = multiple pastes = multiple identical definitions = compilation failure.

Claude2026-01-17 13:41 UTC

Your confusion is understandable, but the indicator is correct.

%K is faster. %D is slower.

The math:

  • %K = raw stochastic (where price is relative to range), smoothed by the "slowing" parameter
  • %D = moving average OF %K

%D is literally derived from %K, so it must lag. It cannot lead what it's averaging.

Looking at your chart: Yellow (%K) is more jagged and reactive. Red (%D) is smoother and trails behind. That's correct behavior.

The crossover signal:

  • %K crossing ABOVE %D = bullish (fast line overtaking slow line = momentum accelerating up)
  • %K crossing BELOW %D = bearish (fast line dropping below slow line = momentum accelerating down)

Same logic as MACD line crossing signal line, or fast MA crossing slow MA.

Where did the misconception come from? Possibly confusion with "Fast Stochastic" vs "Slow Stochastic" - which refers to whether slowing is applied to %K, not which line leads.

Millard2026-01-17 13:42 UTC
explain "fast Stoch" vs. slow
Claude2026-01-17 13:42 UTC

Fast Stochastic:

  • %K = raw calculation (close - lowest low) / (highest high - lowest low)
  • %D = 3-period SMA of %K
  • Very noisy, many whipsaws

Slow Stochastic:

  • %K = 3-period SMA of Fast %K (i.e., what was Fast %D becomes Slow %K)
  • %D = 3-period SMA of Slow %K
  • Smoother, fewer false signals

Your indicator with Slowing=3 is a Slow Stochastic. The "Slowing" parameter applies that initial smoothing to %K before %D is calculated.

If you set Slowing=1, you get Fast Stochastic.

int OnCalculate(const int rates_total,
                const int prev_calculated,
                const datetime &time[],
                const double &open[],
                const double &high[],
                const double &low[],
                const double &close[],
                const long &tick_volume[],
                const long &volume[],
                const int &spread[])
{
   if(rates_total < InpKPeriod + InpSlowing + InpDPeriod - 2) return(0);
   
   int start = (prev_calculated == 0) ? InpKPeriod + InpSlowing - 2 : prev_calculated - 1;
   
   for(int i = start; i < rates_total; i++)
   {
      double sumNum = 0, sumDen = 0;
      for(int s = 0; s < InpSlowing; s++)
      {
         int idx = i - s;
         double hh = high[idx], ll = low[idx];
         for(int k = 1; k < InpKPeriod; k++)
         {
            if(high[idx - k] > hh) hh = high[idx - k];
            if(low[idx - k] < ll) ll = low[idx - k];
         }
         sumNum += close[idx] - ll;
         sumDen += hh - ll;
      }
      KBuffer[i] = (sumDen != 0) ? sumNum / sumDen * 100.0 : 50.0;
   }
   
   start = (prev_calculated == 0) ? InpKPeriod + InpSlowing + InpDPeriod - 3 : prev_calculated - 1;
   
   for(int i = start; i < rates_total; i++)
   {
      if(InpMAMethod == MODE_SMA)
      {
         double sum = 0;
         for(int j = 0; j < InpDPeriod; j++)
            sum += KBuffer[i - j];
         DBuffer[i] = sum / InpDPeriod;
      }
      else if(InpMAMethod == MODE_EMA)
      {
         if(prev_calculated == 0 && i == InpKPeriod + InpSlowing + InpDPeriod - 3)
         {
            double sum = 0;
            for(int j = 0; j < InpDPeriod; j++)
               sum += KBuffer[i - j];
            DBuffer[i] = sum / InpDPeriod;
         }
         else
         {
            double k = 2.0 / (InpDPeriod + 1);
            DBuffer[i] = k * KBuffer[i] + (1 - k) * DBuffer[i - 1];
         }
      }
      else if(InpMAMethod == MODE_SMMA)
      {
         if(prev_calculated == 0 && i == InpKPeriod + InpSlowing + InpDPeriod - 3)
         {
            double sum = 0;
            for(int j = 0; j < InpDPeriod; j++)
               sum += KBuffer[i - j];
            DBuffer[i] = sum / InpDPeriod;
         }
         else
            DBuffer[i] = (DBuffer[i - 1] * (InpDPeriod - 1) + KBuffer[i]) / InpDPeriod;
      }
      else // LWMA
      {
         double sum = 0, wsum = 0;
         for(int j = 0; j < InpDPeriod; j++)
         {
            int w = InpDPeriod - j;
            sum += KBuffer[i - j] * w;
            wsum += w;
         }
         DBuffer[i] = sum / wsum;
      }
   }
   
   return(rates_total);
}
