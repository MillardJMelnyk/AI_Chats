The CIndyPatternMatcher class uses m_low and m_high (inherited from CExpertBase) to find price extremums in ExtStateRSI():

  • Line 265: m_extr_pr[i]=m_low.MinValue(pos-2,5,index);
  • Line 272: m_extr_pr[i]=m_low.MinValue(pos-1,4,index);
  • Line 282: m_extr_pr[i]=m_high.MaxValue(pos-2,5,index);
  • Line 289: m_extr_pr[i]=m_high.MaxValue(pos-1,4,index);

These are CiHigh and CiLow objects — wrappers for the High[] and Low[] price arrays.

The problem:

CExpertBase::InitIndicators() has this logic (lines 381-382):

if(!m_other_symbol && !m_other_period)
   return(true);

Translation: "If we're using the same symbol AND same period as the chart, skip creating timeseries and return immediately."

The framework assumes that when running on the native chart, an outer CExpert object will provide shared timeseries via SetPriceSeries(). But we're using CIndyPatternMatcher standalone — there's no outer Expert providing those pointers.

Result: m_low and m_high stay NULL. First call to m_low.MinValue() crashes.

The fix:

Create CiHigh and CiLow objects manually, initialize them, then pass them to the signal via SetPriceSeries() before calling InitIndicators().

Millard2026-02-05 16:10 UTC
wow, why did they complicate it like that?
Claude2026-02-05 16:10 UTC

The framework was designed for the MQL5 Wizard — a GUI that auto-generates EAs by combining modules.

In that context:

  1. One CExpert orchestrates multiple components (signal, trailing, money management)
  2. All components share the same symbol/period, so creating duplicate CiHigh/CiLow objects for each would waste memory
  3. The parent CExpert creates timeseries once, then passes pointers to all children via SetPriceSeries()

The early return is an optimization: "If you're on the native chart, someone else will give you the data."

Makes sense for the Wizard's architecture. Falls apart the moment you use a signal class standalone — which is a completely reasonable thing to do, but wasn't the primary design target.

Add these inputs at the top with the other inputs:

input bool InpAlertEnabled = true;    // Enable Alerts
input bool InpAlertSound   = true;    // Play Sound

Add this at the end of the main loop in OnCalculate(), inside the for loop, after setting the buffer values:

//--- Alert on new signals (only on most recent completed bar)
if(i == rates_total - 2 && prev_calculated > 0 && InpAlertEnabled)
  {
   if(longSignal > 0)
     {
      Alert(_Symbol, " ", EnumToString(_Period), " - LONG signal (", longSignal, ")");
      if(InpAlertSound) PlaySound("alert.wav");
     }
   if(shortSignal > 0)
     {
      Alert(_Symbol, " ", EnumToString(_Period), " - SHORT signal (", shortSignal, ")");
      if(InpAlertSound) PlaySound("alert2.wav");
     }
  }

The prev_calculated > 0 check prevents alerts on initial load. The i == rates_total - 2 ensures it only fires on the most recently closed bar.
