- `Close - TEMA(9)`

- `abs_dist_to_kc_middle`

A number of strong transition events were centered on `KC Lower`, including:

- fast lines crossing up through `KC Lower`
- fast lines crossing down through `KC Lower`
- touches of `KC Lower` from above and below

Plainly: the lower side of the channel is not missing or weak in the data. It is producing repeated and meaningful behavior.

### 4. Deep downside stretch often led to positive follow-through

The `below_lower` channel regime produced the strongest positive bar-ahead average outcomes in this sample.

Plainly: when price gets pushed materially below the lower Keltner band, rebound behavior often follows.

### 5. Not all crosses are useful

Some crosses had repeatable follow-through. Others were weak, noisy, or misleading.

Plainly: a cross by itself is not a setup. Context still matters.

# BigBrute Relationship Tracking And Analysis Plan

## Purpose

This document summarizes the design decisions we agreed on for tracking BigBrute line relationships, logging full state, and analyzing that data without prematurely imposing signal assumptions.

## Canonical Line Order

The relationship model is built on a fixed logical order that reflects which lines lead.

1. `EMA(2):WCL`
2. `TEMA(9)`
3. `EMA(3):TEMA(9)`
4. `EMA(33):EMA(3):TEMA(9)`
5. `MA(5):(O+C)/2`
6. `KC Upper`
7. `KC Middle`
8. `KC Lower`

This is the canonical relationship order.

It is intentionally separate from:

- plot buffer order
- Data Window order
- any later display rearrangement

That separation was a deliberate design decision so the math does not break if display order changes later.

## Core Design Principle

Do not treat these as unrelated buffers.
Treat them as an ordered stack.

That stack gives us a natural hierarchy:

- `Close` to each line
- each line to the lines below it

This makes the relationship map an ordered upper-triangular structure, not a flat collection of ad hoc variables.

## What We Track

### 1. Raw line values

Store the current value of each line in canonical order:

- `lineValues[8]`

This is not just duplication of plot buffers. It creates a normalized working snapshot that is independent of plot order.

### 2. Close-to-line spreads

Store the signed distance from `Close` to each line:

- `closeSpread[8]`
- formula: `close - lineValues[i]`

This gives 8 direct `Close` relationships.

### 3. Line-to-line spreads

Store the signed distance from each line to every line below it:

- `pairSpread[8][8]`
- valid only where `j > i`
- formula: `lineValues[i] - lineValues[j]`

This gives 28 pairwise relationships.

## Signed-Spread Convention

Signed spreads were chosen as the primary representation.

Meaning:

- positive = above
- negative = below
- zero = touch / within tolerance zone

Examples:

- `EMA(2):WCL - TEMA(9)`
- `EMA(2):WCL - KC Lower`
- `EMA(33):EMA(3):TEMA(9) - MA(5):(O+C)/2`

This signed-distance convention keeps the relationship logic consistent and compact.

## Fudge Factor Rule

We agreed to use a fudge factor so that small values near zero are treated as zero.

Conceptually:

```text
if abs(rawSpread) <= fudge:
    spread = 0
else:
    spread = rawSpread
```

That means all downstream logic sees only:

- positive
- negative
- zero

This avoids unstable micro-noise near exact touches.

## Derived State

We agreed not to store lots of booleans as primary state.

Primary state is:

- current spreads
- previous spreads
- current line values

Derived state is computed on demand from those values.

Examples:

- above / below / touch
- cross up / cross down
- sign flip

If convenience booleans are needed for local logic, they should come from helper functions, not from parallel stored state that can drift out of sync.

## Three-Layer Runtime Model

### 1. Logical line registry

A fixed registry independent of display order.

Each line should know:

- logical ID
- label
- source buffer index

This lets us reorder plots later without breaking the relationship logic.

### 2. Current-bar live snapshot

For the currently open bar, maintain a live tick-level snapshot:

- `lineValues[8]`
- `closeSpread[8]`
- `pairSpread[8][8]`

These are the current, fudged values used for analysis and event detection.

### 3. Previous-state memory

To detect crosses and sign changes, keep prior spreads:

- `prevCloseSpread[8]`
- `prevPairSpread[8][8]`

That is sufficient to derive:

- above / below / touch
- cross up / cross down

without needing to store those as primary flags.

## Per-Tick Method

On each live tick for the open bar:

1. Read the 8 line values into canonical order.
2. Compute `closeSpread[]` with fudge applied.
3. Compute `pairSpread[][]` with fudge applied.
4. Compare current spreads to previous spreads to detect sign changes and crosses.
5. Update previous spreads.

## Closed-Bar Handling

We agreed on this distinction:

1. Historical bars do not have real tick-by-tick truth unless recorded.
2. Tick-by-tick tracking is meaningful for the open bar in live operation.
3. Recently closed bars may be worth keeping for short-memory context, but not forever.

If recent closed-bar intrabar history is useful, keep only a small rolling store.

## Recent-Bar Summary Concept

If we keep closed-bar intrabar memory, it should be compact.

Examples of what to store per bar:

- final spreads
- min spread during the bar
- max spread during the bar
- cross counts
- time/ticks above, below, or zero
- ordering flip count

The point is to preserve useful recent-bar behavior without bloating memory indefinitely.

## Data Capture Philosophy

We explicitly chose discovery over guesswork.

That means:

- do not start with hand-picked signals
- do not hardcode favorite relationships up front
- do not label "bullish" too early
- do not collapse everything into one score before understanding it

Instead, the system should capture full state first, then let the data reveal what matters.

## Sampling Strategy Decision

We decided to prefer full-state capture over early filtering.

That means:

- log every tick for the open bar
- preserve full tick history for recently closed bars if operationally feasible
- export raw relationship state
- analyze offline later

The reasoning was simple:

- don’t pre-filter reality
- don’t bias discovery
- preserve intrabar truth

We agreed that exploding data volume is only a problem if it becomes operationally painful. Until then, over-collection is better than premature filtering.

## Logging Schema Decision

Each recorded sample should capture the full relationship snapshot.

Per sample, store:

- timestamp
- bar time / bar ID
- tick vs bar-close context
- `close`
- all 8 raw line values
- all 8 `Close - Line` spreads
- all 28 pair spreads
- any recent intrabar summary stats if needed later
- forward outcomes for analysis

So each row is a complete market-structure snapshot plus what happened next.

## Architecture Split

We agreed on a layered architecture.

### 1. Feature generator

The relationship engine produces:

- canonical line mapping
- current line values
- close-to-line spreads
- pair spreads
- current vs previous state comparisons

### 2. Sample logger

A separate logger/export layer writes full snapshots to CSV.

### 3. Offline analyzer

Python is the analysis layer.

This is where we do:

- marginal analysis
- joint-state analysis
- regime analysis
- transition analysis
- outcome mining

### 4. Signal extractor

Only after the data identifies useful states or transitions do we encode candidate entry/exit logic.

That sequencing was deliberate. It avoids building rules around guesses.

## Analysis Approach We Agreed On

The analysis should proceed in layers.

### 1. Marginal analysis

Ask one-variable questions first.

Examples:

- when `Close - TEMA(9) > 0`, what happens next?
- when `EMA(2):WCL - TEMA(9)` is strongly positive, what happens next?

### 2. Joint-state analysis

Look at combinations of conditions, not isolated guesses.

Examples:

- all bullish signs aligned
- mixed alignment
- compressed but leaning up
- fully tangled

### 3. Regime analysis

Ask whether the same state behaves differently depending on context.

Examples:

- channel location
- compression width
- stack ordering
- recent cross count / churn

### 4. Transition analysis

This was identified as especially valuable.

The likely gold mine is not just static state, but changes of state:

- below to above
- tangled to aligned
- compressed to expanding
- lead without confirmation to full confirmation

## Data Volume Decision

We explicitly agreed that for this project:

- data capture first
- filtering later

So the correct default was:

- log everything
- analyze everything
- let the data tell us what deserves focus

Operational concerns like speed and file size matter only if they become a real obstacle.

## Practical Implementation Direction

The agreed implementation direction was:

1. use a canonical relationship registry
2. compute signed spreads with fudge applied
3. keep previous spreads for transition detection
4. export full per-tick snapshots to CSV
5. analyze offline in Python
6. extract signals only after the analysis demonstrates useful repeatable structure

## Bottom Line

The agreed plan was to build a data-first relationship engine around a fixed canonical line order, capture the full state of `Close` and all line-to-line relationships every tick, preserve enough recent context to study transitions, and push interpretation into offline Python analysis.

The main intent was to avoid blinders.

We chose:

- full-state capture over guessed signals
- signed spreads over scattered booleans
- logical registry over buffer-order dependency
- offline discovery over premature rule writing

That is the design foundation for the BigBrute relationship analysis work.

# BigBrute Scenario Qualification Framework

## Purpose

This document turns the previously identified evaluation dimensions into a practical decision framework.

It does **not** set final thresholds yet.
It defines:

- what we will measure
- how those measures will be used
- where hard thresholds will eventually apply
- where exceptions may be justified

## Core Principle

The goal is not to pick a single "best" pattern.
The goal is to identify **any productive scenario** whose probability and payoff characteristics are acceptable within risk tolerance.

Win rate remains central.
But win rate is not the only thing that matters.

A scenario may still qualify if:

- its win rate is weaker than ideal
- but its payoff asymmetry is materially better
- and its total behavior still falls within acceptable risk tolerance

So the framework is:

- maximize win rate where possible
- while balancing risk, payoff, stability, and path quality
- and allowing justified exceptions where asymmetry is unusually strong

## The 10 Decision Dimensions

### 1. Sample Size

Question:

- how many times has this scenario actually occurred?

Why it matters:

- small samples produce fragile conclusions
- no scenario should be trusted without enough occurrences

Future use:

- minimum credibility gate
- also used to discount otherwise attractive-looking but under-sampled scenarios

### 2. Directional Win Rate

Question:

- when this scenario occurs, how often does price move in the expected direction?

Why it matters:

- this is the primary success metric
- this remains the central measure in the system

Future use:

- main qualification metric
- probably one of the strongest threshold candidates

### 3. Median Outcome

Question:

- what is the typical result when this scenario occurs?

Why it matters:

- median is more robust than mean
- it tells us whether the scenario is typically productive, not just occasionally spectacular

Future use:

- typical-outcome check
- protects against overreacting to a few extreme winners

### 4. Mean Outcome

Question:

- what is the average result of the scenario?

Why it matters:

- mean still matters for expectancy
- it captures payoff contribution, including exceptional moves

Future use:

- payoff / expectancy assessment
- secondary to win rate, but still important

### 5. Favorable vs Adverse Excursion

Question:

- how far does price usually move in favor before resolution?
- how far does price usually move against before resolution?

Why it matters:

- tradability depends on the path, not just the endpoint
- a scenario can be directionally right but still operationally bad if drawdown is too ugly

Future use:

- core risk tolerance measure
- one of the most important future additions to the analyzer

### 6. Stability Across Horizons

Question:

- does the scenario work only at one horizon, or does it remain productive across nearby horizons?

Why it matters:

- brittle scenarios are harder to trust
- multi-horizon consistency is a sign of structural validity

Future use:

- robustness check
- likely a strong qualification requirement

### 7. Context Stability

Question:

- does the scenario work only in one narrow corner case, or across multiple nearby contexts?

Why it matters:

- scenarios that collapse outside one tiny context are less reliable
- context dependence is not bad, but it should be understood

Future use:

- structural robustness check
- may become part of exception handling

### 8. Symmetry Check

Question:

- does the mirrored form of the scenario behave in an interpretable way?

Why it matters:

- we do not require perfect symmetry
- but asymmetry should be data-demonstrated, not analyst-assumed

Future use:

- analysis integrity check
- helps separate real structure from narrative bias

### 9. Failure Character

Question:

- when the scenario fails, does it fail mildly or badly?

Why it matters:

- some scenarios fail small and often
- others fail rarely but catastrophically
- those are very different risk profiles

Future use:

- risk tolerance / operational suitability
- should be considered alongside win rate, not after it

### 10. Path Coherence

Question:

- does the scenario belong to a recurring sequence the data naturally produces?

Why it matters:

- isolated event fragments are less convincing
- coherent path structure is stronger evidence than one-off triggers

Future use:

- sequence validity check
- especially important for KC middle-line interpretation

## Framework Structure

These 10 dimensions should be used in layers.

### Layer 1: Credibility

A scenario must first be believable.

Primary dimensions:

- sample size
- path coherence
- symmetry check

Purpose:

- reject or downgrade scenarios that are too sparse, too isolated, or too suspiciously one-sided without explanation

### Layer 2: Probability

A scenario must then show directional reliability.

Primary dimensions:

- directional win rate
- median outcome
- stability across horizons

Purpose:

- determine whether the scenario is consistently productive in the intended direction

### Layer 3: Payoff Quality

A scenario must then justify itself economically.

Primary dimensions:

- mean outcome
- favorable vs adverse excursion
- failure character

Purpose:

- determine whether the scenario is worth acting on even if it is not the highest-win-rate case

### Layer 4: Robustness

A scenario must finally survive context checks.

Primary dimensions:

- context stability
- stability across horizons
- symmetry check
- path coherence

Purpose:

- distinguish real structure from accidental local behavior

## Qualification Categories

Instead of a winner/loser ranking, scenarios should eventually be classified.

Recommended categories:

### 1. Qualified

Meaning:

- sufficient sample size
- acceptable directional win rate
- acceptable typical outcome
- acceptable risk profile
- coherent path behavior

### 2. Qualified With Exception

Meaning:

- scenario misses one preferred dimension
- but compensates with unusually strong payoff asymmetry or other strong structural evidence

Typical example:

- lower hit rate than preferred
- but much larger favorable outcome when right
- and still acceptable failure behavior

### 3. Monitor / Needs Refinement

Meaning:

- structurally interesting
- but not yet reliable enough or not yet fully understood

Typical reasons:

- context dependence is still unclear
- path semantics need refinement
- horizon stability is weak

### 4. Reject For Now

Meaning:

- too noisy
- too under-sampled
- too unstable
- too poor a risk profile
- or lacks coherent path structure

## What This Framework Is Not

This framework is **not**:

- a leaderboard
- a single score
- a shortcut to crown a best setup
- a replacement for judgment

Relative performance is informative.
But it becomes operationally relevant mainly when evaluating tradeoffs such as:

- two scenarios both below ideal probability
- one having much stronger payoff asymmetry
- deciding whether the stronger asymmetry justifies inclusion within risk tolerance

## Future Threshold Setting

Thresholds should be chosen only after enough scenario data has been accumulated.

That threshold work should answer questions like:

- what is the minimum sample count for credibility?
- what directional win rate is acceptable?
- how much median or mean outcome is enough?
- how much adverse excursion is too much?
- how much horizon inconsistency is tolerable?
- what kinds of exceptions are allowed?

So the next phase is **not** to set thresholds blindly.
It is to generate enough qualified scenario evidence to make threshold setting defensible.

## Immediate Next Use

This framework should guide the next analysis layer.

The next code should not just rank scenarios.
It should measure scenarios against these dimensions so that later thresholding becomes possible.

That means future analysis outputs should move toward:

- qualification tables
- exception candidates
- instability flags
- path-coherence evidence
- risk-tolerance evidence

## Bottom Line

The framework we agreed on is:

- win rate is primary
- risk/reward is part of the balancing logic
- relative ranking is informative but not decisive
- any scenario that clears tolerance may be useful
- exception handling is valid when payoff asymmetry justifies it

This keeps the project focused on practical scenario qualification rather than winner-picking.

Overall verdict: The architecture and philosophy are genuinely solid. The execution risks are real and most of them come from what isn't in the framework yet, not from what is.

Here's my honest breakdown.

What's actually right

The data-first sequencing is correct. Designing the relationship engine before deciding what matters is the right order of operations. Most retail strategy development does the opposite — picks a setup, then goes looking for confirming data — and produces garbage as a result.

The canonical line registry, signed spreads, and separation of logical order from display order are clean engineering decisions. The three-layer runtime model (registry → live snapshot → previous state) is solid.

The qualification framework is more sophisticated than most analysts ever build. Including adverse excursion, failure character, and path coherence as distinct dimensions shows real operational thinking. Most people stop at win rate and mean return and wonder why live trading is ugly.

The real problems

1. The dataset window is narrow.

19,284 M1 bars is roughly 13–14 trading days of XAUUSD data. That is one regime snapshot. Every finding in this analysis — especially the KC Lower dominance and the below-lower rebound strength — is a statement about what XAUUSD did during that specific two-to-three week stretch, not about structural market behavior. The analysis correctly calls these "candidate setup families," but the language elsewhere is already drifting toward treating them as confirmed.

2. Multiple comparisons problem is unaddressed.

You have 36+ features (8 close spreads + 28 pair spreads) being mined across multiple event types and multiple time horizons. With that many combinations, the strongest-looking relationships are expected to appear strong by random chance alone. The qualification framework has no explicit correction for this — no family-wise error rate consideration, no false discovery rate control, nothing. The top-ranked relationships in a single-period analysis are probably a mix of real structure and selection artifact, and currently there is no way to tell them apart.

3. No out-of-sample discipline.

The qualification framework has robustness checks — context stability, horizon stability, symmetry — but those are all measured within the same dataset. There is no walk-forward partition, no holdout period, no second dataset reserved for confirmation. Without that, the "qualified" designation is really "survived in-sample scrutiny," which is necessary but not sufficient.

4. Execution reality is deferred.

def add_forward_labels(df: pd.DataFrame) -> pd.DataFrame:
    out = df.copy()

        bar_last[f"ret_bar_{horizon}"] = bar_last["bar_close_ref"].shift(-horizon) - bar_last["bar_close_ref"]

def infer_direction(chain: str) -> str:
    score = 0
    up_tokens = [
        "cross_up",
        "below_lower->inside_lower_half",
        "inside_lower_half->inside_upper_half",
        "inside_upper_half->above_upper",
        "fast_mixed->fast_bullish",
        "fast_bearish->fast_mixed",
        "slow_bearish->slow_flat",
        "slow_flat->slow_bullish",
    ]
    down_tokens = [
        "cross_down",
        "above_upper->inside_upper_half",
        "inside_upper_half->inside_lower_half",
        "inside_lower_half->below_lower",
        "fast_mixed->fast_bearish",
        "fast_bullish->fast_mixed",
        "slow_bullish->slow_flat",
        "slow_flat->slow_bearish",
    ]
    for token in up_tokens:
        if token in chain:
            score += 1
    for token in down_tokens:
        if token in chain:
            score -= 1
    return "up" if score >= 0 else "down"


def summarize_path(delta_path: np.ndarray, direction: str) -> tuple[float, float, float]:
    if direction == "up":
        favorable = float(np.max(delta_path))
        adverse = float(np.min(delta_path))
        terminal = float(delta_path[-1])
    else:
        favorable = float(np.max(-delta_path))
        adverse = float(np.min(-delta_path))
        terminal = float(-delta_path[-1])
    return favorable, adverse, terminal


def summarize_arrays(favorable: list[float], adverse: list[float], terminal: list[float]) -> dict[str, float]:
    if not terminal:
        return {}
    fav = np.array(favorable, dtype=float)
    adv = np.array(adverse, dtype=float)
    term = np.array(terminal, dtype=float)
    payoff_ratio = np.nan
    mean_adv = float(np.mean(adv))
    if mean_adv != 0:
        payoff_ratio = float(np.mean(fav) / abs(mean_adv))
    return {
        "sample_count": int(len(term)),
        "mean_terminal": float(np.mean(term)),
        "median_terminal": float(np.median(term)),
        "directional_win_rate": float(np.mean(term > 0)),
        "mean_favorable_excursion": float(np.mean(fav)),
        "mean_adverse_excursion": mean_adv,
        "median_favorable_excursion": float(np.median(fav)),
        "median_adverse_excursion": float(np.median(adv)),
        "payoff_ratio": payoff_ratio,
        "failure_severity": float(abs(np.mean(term[term <= 0]))) if np.any(term <= 0) else 0.0,
    }


def qualification_flags(row: pd.Series) -> dict[str, str]:
    credible_sample = row["sample_count"] >= 100
    directionally_consistent = row["directional_win_rate"] >= 0.60
    payoff_asymmetric = pd.notna(row["payoff_ratio"]) and row["payoff_ratio"] >= 1.50
    failure_tolerable = row["failure_severity"] <= row["mean_favorable_excursion"]
    return {
        "credible_sample": "yes" if credible_sample else "no",
        "directionally_consistent": "yes" if directionally_consistent else "no",
        "payoff_asymmetric": "yes" if payoff_asymmetric else "no",
        "failure_tolerable": "yes" if failure_tolerable else "no",
        "needs_refinement": "yes" if not (credible_sample and directionally_consistent) else "no",
        "exception_candidate": "yes" if (not directionally_consistent and payoff_asymmetric) else "no",
    }

    bar_last_row = np.full(max_bar + 1, -1, dtype=int)
    for row_ix, bar in enumerate(bar_ix):

    accum: dict[tuple[int, str], list[int]] = {}
    for chain_len in CHAIN_LENGTHS:

                if path.size == 0:
                    continue

                fav.append(f); adv.append(a); term.append(t)

            fav, adv, term = [], [], []
            for idx in indices:
                start_bar = int(bar_ix[idx])
                end_bar = start_bar + horizon
                if end_bar > max_bar:
                    continue
                end_row = bar_last_row[end_bar]
                if end_row <= idx:
                    continue

                f, a, t = summarize_path(path - close_vals[idx], direction)

                "chain": chain,
                "direction": direction,
                "target": f"ret_bar_{horizon}",
                **metrics,
            }
            row.update(qualification_flags(pd.Series(row)))
            rows.append(row)

def sign_flip_count(values: pd.Series) -> int:
    arr = values.to_numpy(dtype=float)
    arr = arr[np.isfinite(arr)]
    if arr.size < 2:
        return 0

    signs = np.sign(arr)
    flips = 0
    prev = signs[0]
    for curr in signs[1:]:
        if prev == 0.0:
            prev = curr
            continue
        if curr == 0.0:
            continue
        if curr != prev:
            flips += 1
        prev = curr
    return flips

def evaluate_tick_horizon(close_vals: np.ndarray, indices: np.ndarray, horizon: int, direction: str) -> dict[str, float]:
    fav = []
    adv = []
    final = []
    for idx in indices:
        end = idx + horizon
        if end >= len(close_vals):
            continue
        path = close_vals[idx + 1 : end + 1]
        if path.size == 0:
            continue
        delta_path = path - close_vals[idx]
        if direction == "up":
            favorable = float(np.max(delta_path))
            adverse = float(np.min(delta_path))
        else:
            favorable = float(np.max(-delta_path))
            adverse = float(np.min(-delta_path))
        fav.append(favorable)
        adv.append(adverse)
        final.append(float(delta_path[-1] if direction == "up" else -delta_path[-1]))
    return summarize_arrays(fav, adv, final)


def evaluate_bar_horizon(df: pd.DataFrame, indices: np.ndarray, horizon: int, direction: str) -> dict[str, float]:

    adv = []
    final = []

        start_bar = bar_ix[idx]

def summarize_arrays(favorable: list[float], adverse: list[float], terminal: list[float]) -> dict[str, float]:
    if not terminal:
        return {}
    fav = np.array(favorable, dtype=float)
    adv = np.array(adverse, dtype=float)
    term = np.array(terminal, dtype=float)
    mean_fav = float(np.mean(fav))
    mean_adv = float(np.mean(adv))
    median_term = float(np.median(term))
    mean_term = float(np.mean(term))
    directional_win = float(np.mean(term > 0))
    payoff_ratio = np.nan
    if mean_adv != 0:
        payoff_ratio = mean_fav / abs(mean_adv)
    return {
        "sample_count": int(len(term)),
        "mean_terminal": mean_term,
        "median_terminal": median_term,
        "directional_win_rate": directional_win,
        "mean_favorable_excursion": mean_fav,
        "mean_adverse_excursion": mean_adv,
        "median_favorable_excursion": float(np.median(fav)),
        "median_adverse_excursion": float(np.median(adv)),
        "payoff_ratio": float(payoff_ratio) if not np.isnan(payoff_ratio) else np.nan,
        "failure_severity": float(abs(np.mean(term[term <= 0]))) if np.any(term <= 0) else 0.0,
    }

The code is structurally honest and the architecture is clean. The concerns below are organized roughly by severity.

Serious: iterrows() on 6M rows

Both bigbrute_path_miner.py and bigbrute_path_chain_qualification.py build their event tables by iterating row-by-row through the full dataframe. On 6M ticks that is going to run for a very long time — potentially hours. The path miner is doing the same conceptual work but via a Python loop instead. This is the most operationally impactful problem in the suite.

Moderate: build_events is duplicated

If the event logic needs to change — and it will, as the event taxonomy evolves — it has to change in two places simultaneously.     return (prev > 0) & (series == 0)

This fires only when the spread is exactly zero after fudge. If fudge isn't applied before these series arrive, touch events will be essentially absent. Minor: infer_direction in path_chain_qualification.py is pre-baked

The function assigns a direction to a mined chain based on token scoring. The problem is that a chain the data associates with downside movement will be forced into an "up" label if it happens to contain more up-tokens by the scoring rules. It's a simpler version of bigbrute_scenario_qualification.py — no excursion metrics, just mean/median/win rate. Overall assessment

The design intentions are faithfully reflected in the code. The layering, the separation of feature generation from outcome measurement, and the explicit labeling of flags as non-final are all good. The iterrows problem is the one issue that needs to be addressed before you run this on a large dataset — everything else is refinable without restructuring.

def summarize_path(delta_path: np.ndarray, direction: str) -> tuple[float, float, float]:
    if direction == "up":
        favorable = float(np.max(delta_path))
        adverse = float(np.min(delta_path))
        terminal = float(delta_path[-1])
    else:
        favorable = float(np.max(-delta_path))
        adverse = float(np.min(-delta_path))
        terminal = float(-delta_path[-1])
    return favorable, adverse, terminal


def summarize_arrays(favorable: list[float], adverse: list[float], terminal: list[float]) -> dict[str, float]:
    if not terminal:
        return {}
    fav = np.array(favorable, dtype=float)
    adv = np.array(adverse, dtype=float)
    term = np.array(terminal, dtype=float)
    payoff_ratio = np.nan
    mean_adv = float(np.mean(adv))
    if mean_adv != 0:
        payoff_ratio = float(np.mean(fav) / abs(mean_adv))
    return {
        "sample_count": int(len(term)),
        "mean_terminal": float(np.mean(term)),
        "median_terminal": float(np.median(term)),
        "directional_win_rate": float(np.mean(term > 0)),
        "mean_favorable_excursion": float(np.mean(fav)),
        "mean_adverse_excursion": mean_adv,
        "median_favorable_excursion": float(np.median(fav)),
        "median_adverse_excursion": float(np.median(adv)),
        "payoff_ratio": payoff_ratio,
        "failure_severity": float(abs(np.mean(term[term <= 0]))) if np.any(term <= 0) else 0.0,
    }


def qualification_flags(row: pd.Series, credible_sample_threshold: int, directional_win_rate_threshold: float, payoff_ratio_threshold: float) -> dict[str, str]:
    credible_sample = row["sample_count"] >= credible_sample_threshold
    directionally_consistent = row["directional_win_rate"] >= directional_win_rate_threshold
    payoff_asymmetric = pd.notna(row["payoff_ratio"]) and row["payoff_ratio"] >= payoff_ratio_threshold
    failure_tolerable = row["failure_severity"] <= row["mean_favorable_excursion"]
    return {
        "credible_sample": "yes" if credible_sample else "no",
        "directionally_consistent": "yes" if directionally_consistent else "no",
        "payoff_asymmetric": "yes" if payoff_asymmetric else "no",
        "failure_tolerable": "yes" if failure_tolerable else "no",
        "needs_refinement": "yes" if not (credible_sample and directionally_consistent) else "no",
        "exception_candidate": "yes" if (not directionally_consistent and payoff_asymmetric) else "no",
    }


def evaluate_chains(

    prev = df[state_col].shift(1)

def sign_flip_count(values: pd.Series) -> int:
    arr = values.to_numpy(dtype=float)
    arr = arr[np.isfinite(arr)]
    if arr.size < 2:
        return 0

    signs = np.sign(arr)
    flips = 0
    prev = signs[0]
    for curr in signs[1:]:
        if prev == 0.0:
            prev = curr
            continue
        if curr == 0.0:
            continue
        if curr != prev:
            flips += 1
        prev = curr
    return flips

def evaluate_tick_horizon(close_vals: np.ndarray, indices: np.ndarray, horizon: int, direction: str) -> dict[str, float]:
    fav = []
    adv = []
    final = []

        end = idx + horizon
        if end >= len(close_vals):
            continue

def evaluate_bar_horizon(df: pd.DataFrame, indices: np.ndarray, horizon: int, direction: str) -> dict[str, float]:

def summarize_arrays(favorable: list[float], adverse: list[float], terminal: list[float]) -> dict[str, float]:
    if not terminal:
        return {}
    fav = np.array(favorable, dtype=float)
    adv = np.array(adverse, dtype=float)
    term = np.array(terminal, dtype=float)
    mean_fav = float(np.mean(fav))
    mean_adv = float(np.mean(adv))
    median_term = float(np.median(term))
    mean_term = float(np.mean(term))
    directional_win = float(np.mean(term > 0))
    payoff_ratio = np.nan
    if mean_adv != 0:
        payoff_ratio = mean_fav / abs(mean_adv)
    return {
        "sample_count": int(len(term)),
        "mean_terminal": mean_term,
        "median_terminal": median_term,
        "directional_win_rate": directional_win,
        "mean_favorable_excursion": mean_fav,
        "mean_adverse_excursion": mean_adv,
        "median_favorable_excursion": float(np.median(fav)),
        "median_adverse_excursion": float(np.median(adv)),
        "payoff_ratio": float(payoff_ratio) if not np.isnan(payoff_ratio) else np.nan,
        "failure_severity": float(abs(np.mean(term[term <= 0]))) if np.any(term <= 0) else 0.0,
    }


def qualification_flags(row: pd.Series, credible_sample_threshold: int, directional_win_rate_threshold: float, payoff_ratio_threshold: float) -> dict[str, str]:

    payoff_asymmetric = pd.notna(row["payoff_ratio"]) and row["payoff_ratio"] >= payoff_ratio_threshold
    failure_tolerable = row["failure_severity"] <= row["mean_favorable_excursion"]
    return {

        "payoff_asymmetric": "yes" if payoff_asymmetric else "no",

def add_forward_labels(df: pd.DataFrame) -> pd.DataFrame:
    out = df.copy()

    for horizon in FORWARD_TICK_HORIZONS:
        out[f"ret_tick_{horizon}"] = out["close_ref"].shift(-horizon) - out["close_ref"]

    bar_last = out.groupby("bar_index", as_index=False).agg(bar_close_ref=("close_ref", "last"))
    for horizon in FORWARD_BAR_HORIZONS:
        bar_last[f"ret_bar_{horizon}"] = bar_last["bar_close_ref"].shift(-horizon) - bar_last["bar_close_ref"]

    out = out.merge(
        bar_last[["bar_index"] + [f"ret_bar_{h}" for h in FORWARD_BAR_HORIZONS]],
        on="bar_index",
        how="left",
    )
    return out


def score_outcome(values: pd.Series, direction: str) -> tuple[float, float, float]:
    mean_outcome = float(values.mean())
    median_outcome = float(values.median())
    if direction == "up":
        win_rate = float((values > 0).mean())
    else:
        win_rate = float((values < 0).mean())
    return mean_outcome, median_outcome, win_rate


def evaluate_setups(df: pd.DataFrame, specs: list[dict[str, object]]) -> pd.DataFrame:
    rows: list[dict[str, object]] = []
    targets = [f"ret_tick_{h}" for h in FORWARD_TICK_HORIZONS] + [f"ret_bar_{h}" for h in FORWARD_BAR_HORIZONS]

    for spec in specs:
        mask = spec["trigger"] & spec["context"]
        event_count = int(mask.fillna(False).sum())
        if event_count < MIN_SAMPLES:
            continue
        for target in targets:
            vals = df.loc[mask.fillna(False), target].dropna()
            if len(vals) < MIN_SAMPLES:
                continue
            mean_outcome, median_outcome, win_rate = score_outcome(vals, str(spec["direction"]))
            rows.append(
                {
                    "setup_family": spec["setup_family"],
                    "setup_name": spec["setup_name"],
                    "direction": spec["direction"],
                    "target": target,
                    "sample_count": int(len(vals)),
                    "mean_outcome": mean_outcome,
                    "median_outcome": median_outcome,
                    "win_rate_directional": win_rate,
                    "abs_mean_outcome": abs(mean_outcome),
                    "description": spec["description"],
                }
            )

    if out.empty:
