I want to incorporate Python code into indicators I write on MT5/MQL5. I know of two ways of doing it: web sockets communicating with a Python server, and imported DLLs. what are the advantages of each?
Claude2026-02-03 15:38 UTC

Monday, February 3, 2025, 11:42 AM CST

WebSocket + Python Server

  • Full Python environment: unrestricted access to NumPy, pandas, scikit-learn, TensorFlow, etc. without compilation constraints
  • Hot-swappable: modify Python logic without recompiling or restarting MT5
  • Independent debugging: Python side debuggable with standard tools (pdb, IDE debuggers)
  • Resource isolation: Python runs in separate process/machine; crashes don't take down MT5
  • Scalability: single Python server can service multiple MT5 instances/charts
  • No DLL security prompts in MetaTrader
  • Simpler dependency management: standard pip environment

Imported DLL

  • Lower latency: direct in-process function calls, no network stack or serialization overhead
  • Single deployment unit: no separate server process to manage
  • No network dependency: functions even if network stack has issues
  • Deterministic execution: no connection drops, reconnection logic, or timeout handling needed
  • Simpler architecture for single-indicator use cases

Critical consideration: The DLL approach requires either embedding the Python interpreter in a C/C++ DLL or pre-compiling Python to native code (Cython). You cannot directly import .py files as DLLs. This adds significant build complexity compared to the WebSocket approach where Python runs natively.

For computationally intensive work (ML inference, large dataset analysis), WebSocket is typically preferable despite latency. For ultra-low-latency signal generation where milliseconds matter, DLL wins if you can manage the compilation pipeline.

If you're compiling your own Python code via Cython → C → DLL, that's straightforward: write code, compile, import. Not complex.

The constraint is: what Python functionality do you actually need?

  • Your own algorithms (pure Python logic): Cython compiles this cleanly to a DLL. Minimal friction.

  • Third-party libraries (NumPy, pandas, scikit-learn, TensorFlow): These don't compile out via Cython. They require the Python interpreter at runtime. To use them from a DLL, you'd embed the Python interpreter inside the DLL, which means bundling the Python runtime and managing interpreter initialization/GIL. That's where complexity enters.

So: what's the Python code doing that MQL5 can't?

Millard2026-02-03 15:49 UTC
in MQL5's folder structure, what's the difference between the Include folder and the Library folder?
Claude2026-02-03 15:49 UTC

Include: Source code (.mqh files) inserted at compile time via #include. Becomes part of your compiled .ex5. Header files, class definitions, function libraries in source form.

Libraries: Precompiled binaries (.ex5 libraries compiled with #property library, or .dll files) linked at runtime via #import. Code stays separate, called dynamically.

Key distinction: Include is compile-time text insertion, Libraries is runtime dynamic linking.

Millard2026-02-03 15:52 UTC
OK, once I've got #include code that works how I like it, compile it into an ex5 library module and use it how?
Claude2026-02-03 15:52 UTC
  1. Add #property library at top of the file
  2. Add export keyword after each function signature you want exposed
  3. Save as .mq5 in the Libraries folder
  4. Compile → produces .ex5 in Libraries folder

To use:

#import "YourLibrary.ex5"
   int YourFunction(int param);
   double AnotherFunction(double a, double b);
#import

Then call functions directly. You must declare the signatures in the #import block—the compiler doesn't read them from the .ex5.

Millard2026-02-03 15:53 UTC

Claude2026-02-03 15:53 UTC

No. The functions are callable, but they're external calls resolved at runtime, not inlined.

Practical difference: you must manually declare every function signature in the #import block. The compiler doesn't know what's inside the .ex5—it trusts your declarations. If you get a signature wrong, it fails at runtime, not compile time.
